# 元の設計案(構成・依存方向)と hnk-next との比較

別の場所で実装を進めている人へ渡すための資料。この資料だけで読めるように書く。
元の案は「Go の設計思想を Hono (TypeScript) で再現する」という相談の中で出たもの。
hnk-next (https://github.com/ashunar0/hnk-next) を読んだ上での比較も末尾に付ける。

---

## 1. 元の設計案

### 1.1 ファイル構成 (ドメインで縦に切り、中を役割で分ける)

```
src/
├─ modules/
│  ├─ orders/
│  │  ├─ domain.ts       # 型と業務ロジック。外を知らない
│  │  ├─ ports.ts        # interface (StockChecker, OrderRepo)
│  │  ├─ schema.ts       # Zod スキーマ (入出力の形)
│  │  ├─ routes.ts       # createRoute + ハンドラ (HTTP の翻訳)
│  │  ├─ repo.pg.ts      # ports の Postgres 実装
│  │  ├─ index.ts        # 他モジュールへの公開口
│  │  └─ domain.test.ts  # 偽物を渡すテスト
│  └─ users/ (同じ構成)
├─ shared/
│  ├─ tenant.ts          # TenantId (ブランド型)
│  └─ result.ts          # Result 型
├─ app.ts                # buildApp (全モジュールをつなぐ唯一の場所)
└─ entry/
   ├─ node.ts            # Node 用の起動
   └─ worker.ts          # Workers 用の起動
```

- 「routes/ services/ repos/」のように技術の種類で横に切らない
- 最初から全部作らず、1 ファイルで始めて「2 つの理由で変更しそう」と感じたら分ける
- ただし `domain` だけは最初から分けておく

### 1.2 依存の向き

```
routes ──→ domain ←── repo.pg
              ↑
            ports
```

矢印は「import する」向き。**domain は誰も import しない**。周りが全部 domain に向かう。

| ファイル | import してよいもの |
|---|---|
| domain.ts | 同モジュールの ports (型)、shared |
| ports.ts | domain の型、shared |
| routes.ts | domain、schema、shared |
| repo.pg.ts | ports、domain の型、DB ライブラリ |
| app.ts / entry/ | 全部 (本物の実装を作って渡す唯一の場所) |

### 1.3 機械で強制するルール (dependency-cruiser で書く想定)

- `domain-is-pure`: domain / ports は hono・zod・`node:*` を import しない
- `domain-no-outward`: domain は routes・repo・schema を import しない
- `no-cross-module-deep-import`: 他モジュールは `index.ts` 経由のみ

補助 (oxlint / ESLint):

- `no-floating-promises`: `await` 忘れを禁止
- domain 内の `throw` を禁止 (`Result` で返す)
- `process.env` の直読みを禁止 (Config 注入に統一)

### 1.4 途中で足した設計

**DI は引数で渡す**

```ts
export function buildApp(deps: Deps) {
  const app = new Hono()
  app.route("/orders", ordersRoutes(deps))
  return app
}
```

Workers ではリクエストをまたいだ I/O (DB 接続など) が使えないため、のちに
「組み立てた結果」ではなく「組み立て方 (`makeDeps(env)`)」を渡す形に直した。

**テナント分離は構造で守る**

- DB 側: PostgreSQL の RLS + `set_config('app.tenant_id', ..., true)` (トランザクション内だけ有効)
- アプリ側: `TenantDbProvider.run(tenantId, fn)` の中でしか `TenantDb` が手に入らない
- リポジトリは `TenantDb` を要求するので、`run` の外では呼べない
- 失敗した `Result` や例外ならロールバックされる

**失敗の扱い**

```ts
type Result<T> = { ok: true; value: T } | { ok: false; error: string }
```

domain では `throw` せず `Result` で返す。HTTP のステータスへの変換は routes の仕事。

**DB の抽象化**

「SQL 方言の抽象化」ではなく「テナント分離戦略の抽象化」をする。
SQL は repo に閉じ込め、分離方式 (共有 + RLS か、テナントごとの物理分離か) は
`TenantDbProvider` の中身だけの違いにする。契約テストで全アダプターを同じ基準で検証する。

## 2. hnk-next との比較

### 2.1 対応表

| 役割 | 元の案 | hnk-next |
|---|---|---|
| モノ + 入力ルール | `domain.ts` | `contract/<f>/model.ts` (zod の brand) |
| 保存の形の宣言 | `ports.ts` | `service.ts` 内の `InvoicesRepository` |
| 業務ロジック | `domain.ts` | `service.ts` |
| 保存の実装 | `repo.pg.ts` | `repository.ts` + `table.ts` |
| HTTP | `routes.ts` | `route.ts` + `presenter.ts` |
| 入出力の形 | `schema.ts` | `contract/<f>/schema.ts`, `type.ts` |
| 組み立て | `app.ts` + `entry/` | `deps.ts` + `index.ts` |

### 2.2 hnk-next のほうが進んでいる点

- **`contract/` をフロントと共有する**: TS の強みを活かした発想。元の案にはなかった
- **失敗が閉じた型**: service は `"NOT_FOUND" | "NOT_OWNER"` のようなコードだけを返し、HTTP への変換は宣言側が持つ。元の案の `error: string` より明確
- **依存を引数で受ける**: route が service / repository を import しない
- **interface を使う側で宣言する**: `ports.ts` を作らず service.ts に置く (Go 流で局所性が高い)
- **`reply` と `guard`**: 宣言と応答のずれ、401 の宣言忘れが型で止まる

### 2.3 元の案にあって、hnk-next にまだ無いもの

| 項目 | 内容 |
|---|---|
| テナント / 所有者の境界 | `scopeTo` は「どの table に書けるか」(feature 軸) だけを縛る。「誰の行か」は各 service の手書き |
| トランザクション境界 | feature をまたぐ書き込みの置き場所 (`usecases/`) が未設計。lint メッセージには出てくるが存在しない |
| 依存方向の機械強制 | lint は「service → repository 禁止」と feature 越境禁止だけ。他は未強制 |
| 時刻・ID の注入 | service が `crypto.randomUUID()` / `new Date()` を直接呼んでいる |

### 2.4 設計上の論点

**論点 A: domain と zod の関係 (一番大きな違い)**

- 元の案: domain は zod を import しない。スキーマは `schema.ts` に分ける
- hnk-next: ルールを zod で `contract/model.ts` に置き、service はブランド付きの型だけを受け取る

hnk-next の形は Go の「入力の検査はモノの側に置く」に近く、フロントとルールを共有できる利点がある。
代償は、ドメインの検証言語が zod に固定されること。どちらに寄せるかを決めて明文化したい。

**論点 B: 依存の向きがファイル名の約束止まり**

Go は package 境界が向きを物理的に強制するが、hnk-next は 1 つの feature フォルダに 5 ファイルが同居し、
向きの強制は 2 種類の lint だけ。次は止まらない。

- `route.ts` が `./repository` や `../../db` を import して drizzle を直接叩く
- `service.ts` が `../../db` を import する

役割ごとの import **許可リスト**を 1 枚の表にして lint にするのがよい。

| 役割 | 許可する import |
|---|---|
| route | hnk, contract, errors, middleware, presenter |
| service | hnk, contract/model, table (型のみ) |
| repository | drizzle, db, service (型のみ), table |
| presenter | contract/type, table (型のみ) |

**論点 C: `usecases/` の設計**

serviceが他 feature の repository / service に触れないため、feature をまたぐ書き込みの置き場所がない。
ここが D1 の `batch` や Postgres のトランザクションの境界になる。決め方の候補:

- 常に usecase 経由 (薄くてもよい)
- service を直接呼んでよい条件を lint で決める

二本立てで曖昧なままにすると、AI が迷う原因になる。

**論点 D: service のデータ型が DB の行そのもの**

service が `table.ts` の `InvoiceRow` を import している。Rails 流の割り切りとしては成立するが、
`conventions.md` の #37 (行とドメインの型を分ける) と食い違う。どちらかに決めて書く。
現状は `InvoiceUpdateValues = Partial<NewInvoiceRow>` により `id` や `ownerId` も更新できてしまう。

### 2.5 命名・ヘルパーの指摘

- 失敗を表す語が 4 つある: `err()` (Result で返す) / `reply.failure()` (handler が返す) / `fail()` (throw) / `httpError()` (定義)。
  `fail` (投げる) と `failure` (返す) は別チャネルなのに似すぎ。`abort` などへの改名を検討
- `contract/` に「ドメインのルール (model)」と「HTTP の入出力 (schema, type)」が同居していて、`contract` の語が曖昧
- 複数形 / 単数形の規則が暗黙 (`import { invoices as invoicesTable }` の alias は衝突のサイン)
- 「無いと書けてしまう間違い」の基準に当てはめて足りないもの:
  - DB の行をそのまま応答に返せる (`reply` の型検査は構造的で、余計な列を持つ行も通りうる)
  - 所有者チェックを書き忘れられる (`authorize(row, viewerId)` のような方針の一元化)
  - 時刻と ID の注入
  - 複数書き込みの境界

### 2.6 小さな穴 (順次修正予定のもの)

- 同じステータスの失敗が 2 つあると、型は通って実行時に throw する → 起動時に検出する
- update / delete が「確認 → 書き込み」の 3 手で、D1 では原子的にできない → 所有者条件を WHERE に押し込む
- `get` は他人の行を NOT_FOUND にするが、update / delete は NOT_OWNER を返す (存在の漏れが不統一)
- `no-module-scope-state` が `const x = []` や `{}` を見逃す。モジュール直下の DB クライアント生成も未検出
- `no-foreign-repository` は相対 import だけ解決する (エイリアス経由は素通り)
- `route-declares-auth` は名前の正規表現で判定している (型で縛る形のほうが強い)
- リクエストごとに作ったクライアントの後始末の口が `provideDeps` に無い (Hyperdrive 移行時に必要)

## 3. 次にやるとよいこと

1. 役割ごとの依存許可表を 1 枚にして lint 化する (論点 B)
2. `usecases/` の方針を決める (論点 C)
3. domain と zod の関係を決めて、README に書く (論点 A)
4. 2 つ目の feature を AI に書かせ、型と lint で止まらなかった間違いを記録して、仕組みに昇格する

## 4. 調査の範囲

読んだもの: README、`conventions.md`、`hnk/src/index.ts`、`hnk/lint.mjs`、`deps.ts`、`api/index.ts`、
`.oxlintrc.json`、invoices の route / service / repository / table / presenter、`contract/` 一式、`db/index.ts`、
`middleware/auth.ts`、`errors.ts`。
読んでいないもの: Go 側の実装、`tsconfig`、typetest、repo 内の `memo.md`。
