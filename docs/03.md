# 場面ごとに形を試す

invoices の CRUD だけで磨いた形が、他の場面でも同じように書けるかを試す記録。
1 場面ずつ、書く前に「育ち方の表のどの動きで、何が増えるはずか」を予想し、書いた後に答え合わせをする。

今は形だけを見る段階。lint やルールの整備は、全部の場面を見てからまとめてやる。
実行時の確認（D1 に繋いで動かす）はしていない。typecheck と lint まで。

| #   | 場面                                | 状態 |
| --- | ----------------------------------- | ---- |
| 1   | 検索とページネーション              | 済   |
| 2   | ロールによる認可                    | 済   |
| 3   | 外部 API（保存じゃない外との接点）  | 済   |
| 4   | webhook と、module をまたぐ書き込み | 済   |
| 5   | cron とキュー                       |      |
| 6   | 集計                                |      |

## 1. 検索とページネーション

invoices の一覧に、状態（draft / sent / paid）での絞り込みと、カーソルでのページ送りを足した。

### 予想

新しいファイルは要らない。既存の 4 ファイルの中で収まる（育ち方のどの動きにも当たらない）。

### 結果

予想どおり、ファイルは増えなかった。それぞれの置き場所はこうなった。

| もの                                                                               | 置き場所                   | 理由                                           |
| ---------------------------------------------------------------------------------- | -------------------------- | ---------------------------------------------- |
| 状態の種類（`invoiceStatuses`）                                                    | domain                     | モノの性質                                     |
| 新規作成は下書き                                                                   | service                    | 手順のルール                                   |
| 一覧の条件・ページ・位置の型（`InvoiceListQuery`、`InvoicePage`、`InvoiceCursor`） | service                    | 手順が保存に求める形。保存の形の宣言と並ぶ     |
| 1 件多く読んで続きを知る、キーセットの WHERE                                       | repo                       | 保存の技法                                     |
| カーソルを外から読めない文字列にする（base64）                                     | routes                     | HTTP での見せ方。Date を数値にするのと同じ種類 |
| 壊れたカーソルを 400 にする                                                        | routes（zod の transform） | 検査の失敗として自動で 400 になる              |
| limit の既定値と上限                                                               | routes                     | HTTP の入口でシステムを守る値                  |

### 引っかかったこと

1. **repo が domain の値を使いたくなった。** テーブルの `status` 列の取りうる値を `invoiceStatuses` から借りるため。
   DB の制約が domain のルールを写すのは自然なので、許可表を「repo → domain は値も可」に緩めた
2. **routes が service の型に名前で触れない。** ページの変換関数の引数に `InvoicePage` を使いたかったが、
   routes → service は禁止なので、`{ items: Invoice[]; next: Pick<Invoice, "updatedAt" | "id"> | null }` と構造で書いた。
   二重に書いている。routes → service を「型だけ可」にするかは未決
3. **query を宣言すると、hc で呼ぶときに引数が必須になる。** 項目が全部省略可能でも `$get({ query: {} })` と書く必要がある。形の問題ではなく使い勝手の話

### 確かめていないこと

- zod の transform を含む query で、`/openapi.json` の生成が通るか（実行時の話なので未確認）
- キーセットの WHERE が D1 で意図どおりに動くか

## 2. ロールによる認可

閲覧者に member / admin のロールを持たせた。

- 触れる範囲: admin は全員の請求書に、member は自分のものだけに触れる
- できる操作: 送付（draft → sent）は admin だけ。下書きでなければ送れない

### 予想

範囲と操作のルールは domain の純粋な関数に書け、ファイルは増えない。
ただし `Viewer`（閲覧者とロール）は invoices の概念ではないので、置き場所が育ち方の表に無い。
Go 版の `user` パッケージに倣って `modules/users/domain.ts` に置くことになる。

### 結果

invoices の中は、ファイルが増えなかった。`modules/users/domain.ts` が増えた（domain だけの module）。

| もの                                                 | 置き場所           | 理由                                                           |
| ---------------------------------------------------- | ------------------ | -------------------------------------------------------------- |
| `Viewer`、`Role`                                     | users の domain    | 利用者というモノ。invoices からは型だけ借りる                  |
| 触れる範囲（`InvoiceReach`、`reachOf`）              | invoices の domain | ロールから範囲が決まる、データだけで答えが出るルール           |
| できる操作（`canSend`）、状態の遷移（`isSendable`）  | invoices の domain | 同上                                                           |
| 確認の順番（NOT_FOUND → FORBIDDEN → NOT_DRAFT）      | service            | 手順。範囲の外は在ることを知らせないので、NOT_FOUND を先に返す |
| 範囲と状態を WHERE にする（`within(reach)`、`from`） | repo               | 保存の技法。確認と書き込みの間に状態が変わっても壊れない       |
| 失敗の番号（403、409）                               | errors と routes   | HTTP の翻訳                                                    |

所有者だけだった WHERE は、「範囲」に一般化すると素直に広がった。
`updateOwned(id, ownerId)` → `updateWithin(id, reach)` で、admin は `{ kind: "all" }` になり条件が消える。

### 引っかかったこと

1. **他 module の domain を型で借りる必要があった。** invoices の domain が users の `Viewer` を使う。
   Go 版でも `invoice` が `user` を import している。許可表を「domain / service → 他 module の domain は型だけ可」に緩めた
2. **service が domain の関数を呼ぶ必要があった。** `reachOf` などは domain の純粋な関数なので、「service → domain は型だけ」では呼べない。
   許可表を「service → domain は値も可」に緩めた。domain がルールを関数で持つ以上、これが本来の形
3. **domain だけの module ができた。** users は認証の実装がまだ無いので、domain.ts しかない。
   出発点の「4 ファイルで始める」に当てはまらない。モノが他の module から型として参照されるだけなら、domain だけで足りる
4. **service が Viewer を受け取るので、cron から呼ぶときに「誰として呼ぶか」が要る。** 場面 5 で考える
5. **「送付」は admin だけ、をどこで止めるか。** routes の guard（`requireAdmin`）でも止められるが、それだと HTTP 以外の入口では素通りする。
   ルールは domain に置き、service で確かめた。guard は「画面ごと admin 専用」のような HTTP の都合のときに使う、と分けるのがよさそう

## 3. 外部 API（保存じゃない外との接点）

payments module を足した。送付済みの請求書に対して、決済サービス（Stripe）の支払い画面を作り、支払いを記録する。
そのために invoices に金額（`amount`）を足した。

### 予想

- payments は出発点の 4 ファイル＋外部 API のアダプター 1 つ（`gateway.stripe.ts`）。名前は `repo.d1.ts` と同じ「役割.技術名」
- 決済サービスに求める形は service で宣言する（保存の形と同じやり方）
- 請求書を読む必要があるが、payments の service が invoices を import するのは禁止。
  payments 側で「請求書に求める形」を宣言し、deps.ts で invoices の service をつなぐ

### 結果

予想どおりの形になった。

```
api/modules/payments/
├─ domain.ts           Payment の型と状態
├─ service.ts          手順。保存・決済サービス・請求書に求める形を 3 つ宣言する
├─ routes.ts           POST /payments
├─ repo.d1.ts          payments テーブル
└─ gateway.stripe.ts   PaymentGateway を Stripe で満たす
```

| もの                                       | 置き場所                                  | 理由                                                                                |
| ------------------------------------------ | ----------------------------------------- | ----------------------------------------------------------------------------------- |
| 決済サービスに求める形（`PaymentGateway`） | payments の service                       | 使う側が宣言する。Stripe の API の形や認証は出さない                                |
| Stripe の API を呼ぶ                       | gateway.stripe.ts                         | アダプター。repo.d1.ts と同じ位置                                                   |
| 請求書に求める形（`PayableInvoices`）      | payments の service                       | 使う側が宣言する。payments は invoices を import しない                             |
| 支払えるのは送付済みだけ（`isPayable`）    | invoices の domain                        | 請求書のルール                                                                      |
| 支払える請求書を返す（`getPayable`）       | invoices の service                       | 上のルールを使う手順                                                                |
| つなぐ                                     | deps.ts（`this.invoices` をそのまま渡す） | invoices の service が構造で `PayableInvoices` を満たすので、間に詰め替えが要らない |
| 秘密鍵・戻り先の URL                       | env → deps → gateway                      | domain と service は env を知らない                                                 |
| 決済サービスの失敗                         | Result の `GATEWAY_FAILED` → 502          | 想定内の失敗として扱った                                                            |

module をまたぐ読みが、import 無しで書けた。Go の「interface は使う側が決める」がそのまま効いている。
payments の service は invoices を一切 import せず、deps.ts だけが両方を知っている。

### 引っかかったこと

1. **gateway は lint の対象外。** 許可表に `gateway` の役割が無いので、gateway.stripe.ts が何を import しても止まらない（試して 0 件）。
   アダプターの役割（repo、gateway、これから出る cron など）を表にどう載せるかを決める必要がある
2. **payments の repo が invoices の repo を import した。** 外部キー（`references(() => invoicesTable.id)`）のため。
   許可表の「他 module の repo」で通るが、DB の層で module がつながっていることになる
3. **invoices の service に、payments のためのメソッド（`getPayable`）が増えた。** ルールは invoices のものなので invoices に置くのが正しいが、
   他の module が増えるたびに「誰かのための入口」が増えていく。1.1 の `index.ts`（公開口）が要るのはこういうときかもしれない
4. **外部 API と DB の書き込みは、まとめて取り消せない。** 先に決済画面を作り、後で記録した。逆だと、決済に失敗したとき使われない支払いが残る。
   今の順番だと、記録に失敗したときに使われない決済画面が残る（Stripe 側で期限切れになるので害は小さい）。順番の判断を毎回書く人に委ねている
5. **外部 API の失敗を想定内にするか、想定外にするか。** 今回は Result で返した（502）。throw にすると onError で 500 になる。基準が無い

## 4. webhook と、module をまたぐ書き込み

Stripe から支払い完了の通知が来たら、署名を確かめ、支払いを succeeded にし、請求書を paid にする。

### 予想

- webhook は 2 つ目の入口なので「横に増える」。`payments/webhook.stripe.ts` が routes.ts の隣に並ぶ
- 署名の確かめ方は Stripe の知識なので gateway に置く
- 支払いと請求書の両方に書くので「上に載る」。初めての `usecases/` ができる。usecase も「求める形」を自分で宣言し、deps.ts でつなぐ
- D1 にはトランザクションが無いので、2 つの書き込みを「何度やっても同じ結果になる」手順にし、途中で落ちたら Stripe の再送でやり直す

### 結果

予想どおりの形になった。

```
api/
├─ usecases/
│  └─ settle-payment.ts       支払いを成功にし、請求書を支払い済みにする
└─ modules/payments/
   ├─ webhook.stripe.ts       2 つ目の入口。ログインではなく署名で確かめる
   └─ gateway.stripe.ts       verifyEvent を追加（署名と、Stripe の通知 → PaymentEvent）
```

| もの                                                   | 置き場所                          | 理由                                                                           |
| ------------------------------------------------------ | --------------------------------- | ------------------------------------------------------------------------------ |
| 支払いの結果（`PaymentEvent`）                         | payments の domain                | Stripe の通知を、このアプリの言葉に読み替えたもの                              |
| 署名の確かめ方、Stripe の通知の種類の読み替え          | gateway.stripe.ts                 | Stripe の知識                                                                  |
| 支払いを成功 / 失敗にする（何度呼んでも同じ）          | payments の service               | 1 つの module の中の操作                                                       |
| 請求書を支払い済みにする（何度呼んでも同じ）           | invoices の service（`markPaid`） | 同上                                                                           |
| 2 つを順に呼ぶ                                         | usecases/settle-payment.ts        | 2 つの module に書く。使う形を自分で宣言し、deps.ts で 2 つの service が満たす |
| 受け取った本文のまま署名を確かめる、通知の種類で分ける | webhook.stripe.ts                 | 入口                                                                           |

usecase も module と同じく、どの module も import せずに書けた。deps.ts の 1 行（`settlePayment(this.payments, this.invoices)`）でつながる。
トランザクションの代わりに「何度やっても同じ結果」にする手順は、invoices の `markPaid` で 3 通り（書き換えた・もう支払い済み・それ以外）を分ける必要があった。

### 引っかかったこと

1. **webhook と usecase は、lint に丸ごと見逃される。** わざと違反を 3 種類書いても 0 件だった
   （他 module の repo を import、認証の指定なし、`c.json` で返す）。
   routes の規則（認証の指定、reply で返す、export は束 1 本）は「ファイル名が routes.ts」で判定しているので、入口が増えると効かない。
   許可表（`layer-imports`）も、知らない役割は素通りする。**場面 3 の gateway と合わせて、lint の一番大きな穴**
2. **閲覧者を取らない操作（`markPaid`）が、invoices の service に普通に並んでいる。** routes から呼べば、範囲の確認を飛ばして支払い済みにできてしまう。
   システムだけが行う操作を、利用者の操作と分ける仕組みが無い
3. **webhook の handler に分岐が入った。** 通知の種類（成功 / 失敗）で、usecase と payments のどちらを呼ぶかを分けている。
   入口が「取り出す → 処理する → 返す」より厚くなる。通知を受ける usecase（`receivePaymentEvent`）にまとめる手もある
4. **入口ごとに、失敗の意味が違う。** webhook で NOT_FOUND を 404 で返すと、Stripe は何日も再送してくる。
   利用者向けの routes と同じ「失敗 → HTTP の番号」の対応でよいかは、入口ごとに考える必要がある
5. **「何度やっても同じ結果」にする重さを、各 service が負う。** D1 の `batch` でまとめて書く道もあるが、
   repo が「すぐ実行する関数」ではなく「まとめられる文」を返す形にしないといけない。今は採っていない

### 見直し: usecases/ をやめて commands/ にした

最初は `api/usecases/settle-payment.ts` を module の外に置いたが、置き直した。

「usecase」は流派によって指すものが違う。クリーンアーキテクチャでは操作すべて、モジュラーモノリスでは module の公開入口、
DDD では複数のモノを動かす手順。前の hnk（hono-backend スキル）の `usecases/` は 2 番目で、
「この domain が、他の domain に変えさせてよい操作」だった。最初に作ったものは 3 番目で、名前だけが同じだった。

module をまたぐ書き込みについては、流派が違っても答えが揃っている。

- DDD（Effective Aggregate Design）: 1 回の書き込みで変えるモノは 1 つ。またぐ整合性は後から追いつかせる
- モジュラーモノリス: 他の module の中身に触らない。相手が公開した入口だけを使う
- Go: interface は使う側が決める。手順は流れの持ち主が持つ

判断の基準を「無いと書けてしまう間違いを言えるか」「1 回の書き込みで 1 module か」「矢印と、使う側の宣言」「名前が世の中の使い方とぶつからないか」とし、
全部を満たす形にした。

```
modules/payments/service.ts            receive(event): 流れの持ち主。支払いを成功にしてから、請求書を頼む
modules/invoices/commands/markPaid.ts  invoices が外に変えさせてよい操作。1 操作 1 ファイル
```

- 名前は CQRS の「状態を変える操作」から `commands/`。クリーンアーキテクチャの usecase と混ざらない
- `markPaid` は invoices の service から外した。deps.ts は commands を routes に渡さず、payments にだけ渡すので、**routes から支払い済みにはできない**（引っかかり 2 が解けた）
- 他の module のための書き込みは commands に 1 ファイルずつ並ぶので、invoices の service は膨らまない（場面 3 の引っかかり 3 のうち、書きの側が解けた。読みの `getPayable` は service に残る）
- 成功と失敗の分岐は payments の service（`receive`）に入れたので、webhook は「確かめる → 渡す → 返す」に戻った（引っかかり 3 が解けた）
- 育ち方の表の「上に載る」は「窓口を開く」に置き換えた。他の module が書きに来たら、書かれる側に `commands/` を開く。読みに来るときは何も足さない

lint はまだ commands を知らない（許可表に役割が無い）。全部の場面を見た後に整える
