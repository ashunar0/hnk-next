# 場面ごとに形を試す

invoices の CRUD だけで磨いた形が、他の場面でも同じように書けるかを試す記録。
1 場面ずつ、書く前に「育ち方の表のどの動きで、何が増えるはずか」を予想し、書いた後に答え合わせをする。

今は形だけを見る段階。lint やルールの整備は、全部の場面を見てからまとめてやる。
実行時の確認（D1 に繋いで動かす）はしていない。typecheck と lint まで。

| #   | 場面                                | 状態 |
| --- | ----------------------------------- | ---- |
| 1   | 検索とページネーション              | 済   |
| 2   | ロールによる認可                    | 済   |
| 3   | 外部 API（保存じゃない外との接点）  |      |
| 4   | webhook と、module をまたぐ書き込み |      |
| 5   | cron とキュー                       |      |

## 1. 検索とページネーション

invoices の一覧に、状態（draft / sent / paid）での絞り込みと、カーソルでのページ送りを足した。

### 予想

新しいファイルは要らない。既存の 4 ファイルの中で収まる（育ち方のどの動きにも当たらない）。

### 結果

予想どおり、ファイルは増えなかった。それぞれの置き場所はこうなった。

| もの                                                                               | 置き場所                   | 理由                                           |
| ---------------------------------------------------------------------------------- | -------------------------- | ---------------------------------------------- |
| 状態の種類（`invoiceStatuses`）                                                    | domain                     | モノの性質                                     |
| 新規作成は下書き                                                                   | service                    | 手順のルール                                   |
| 一覧の条件・ページ・位置の型（`InvoiceListQuery`、`InvoicePage`、`InvoiceCursor`） | service                    | 手順が保存に求める形。保存の形の宣言と並ぶ     |
| 1 件多く読んで続きを知る、キーセットの WHERE                                       | repo                       | 保存の技法                                     |
| カーソルを外から読めない文字列にする（base64）                                     | routes                     | HTTP での見せ方。Date を数値にするのと同じ種類 |
| 壊れたカーソルを 400 にする                                                        | routes（zod の transform） | 検査の失敗として自動で 400 になる              |
| limit の既定値と上限                                                               | routes                     | HTTP の入口でシステムを守る値                  |

### 引っかかったこと

1. **repo が domain の値を使いたくなった。** テーブルの `status` 列の取りうる値を `invoiceStatuses` から借りるため。
   DB の制約が domain のルールを写すのは自然なので、許可表を「repo → domain は値も可」に緩めた
2. **routes が service の型に名前で触れない。** ページの変換関数の引数に `InvoicePage` を使いたかったが、
   routes → service は禁止なので、`{ items: Invoice[]; next: Pick<Invoice, "updatedAt" | "id"> | null }` と構造で書いた。
   二重に書いている。routes → service を「型だけ可」にするかは未決
3. **query を宣言すると、hc で呼ぶときに引数が必須になる。** 項目が全部省略可能でも `$get({ query: {} })` と書く必要がある。形の問題ではなく使い勝手の話

### 確かめていないこと

- zod の transform を含む query で、`/openapi.json` の生成が通るか（実行時の話なので未確認）
- キーセットの WHERE が D1 で意図どおりに動くか

## 2. ロールによる認可

閲覧者に member / admin のロールを持たせた。

- 触れる範囲: admin は全員の請求書に、member は自分のものだけに触れる
- できる操作: 送付（draft → sent）は admin だけ。下書きでなければ送れない

### 予想

範囲と操作のルールは domain の純粋な関数に書け、ファイルは増えない。
ただし `Viewer`（閲覧者とロール）は invoices の概念ではないので、置き場所が育ち方の表に無い。
Go 版の `user` パッケージに倣って `modules/users/domain.ts` に置くことになる。

### 結果

invoices の中は、ファイルが増えなかった。`modules/users/domain.ts` が増えた（domain だけの module）。

| もの                                                 | 置き場所           | 理由                                                           |
| ---------------------------------------------------- | ------------------ | -------------------------------------------------------------- |
| `Viewer`、`Role`                                     | users の domain    | 利用者というモノ。invoices からは型だけ借りる                  |
| 触れる範囲（`InvoiceReach`、`reachOf`）              | invoices の domain | ロールから範囲が決まる、データだけで答えが出るルール           |
| できる操作（`canSend`）、状態の遷移（`isSendable`）  | invoices の domain | 同上                                                           |
| 確認の順番（NOT_FOUND → FORBIDDEN → NOT_DRAFT）      | service            | 手順。範囲の外は在ることを知らせないので、NOT_FOUND を先に返す |
| 範囲と状態を WHERE にする（`within(reach)`、`from`） | repo               | 保存の技法。確認と書き込みの間に状態が変わっても壊れない       |
| 失敗の番号（403、409）                               | errors と routes   | HTTP の翻訳                                                    |

所有者だけだった WHERE は、「範囲」に一般化すると素直に広がった。
`updateOwned(id, ownerId)` → `updateWithin(id, reach)` で、admin は `{ kind: "all" }` になり条件が消える。

### 引っかかったこと

1. **他 module の domain を型で借りる必要があった。** invoices の domain が users の `Viewer` を使う。
   Go 版でも `invoice` が `user` を import している。許可表を「domain / service → 他 module の domain は型だけ可」に緩めた
2. **service が domain の関数を呼ぶ必要があった。** `reachOf` などは domain の純粋な関数なので、「service → domain は型だけ」では呼べない。
   許可表を「service → domain は値も可」に緩めた。domain がルールを関数で持つ以上、これが本来の形
3. **domain だけの module ができた。** users は認証の実装がまだ無いので、domain.ts しかない。
   出発点の「4 ファイルで始める」に当てはまらない。モノが他の module から型として参照されるだけなら、domain だけで足りる
4. **service が Viewer を受け取るので、cron から呼ぶときに「誰として呼ぶか」が要る。** 場面 5 で考える
5. **「送付」は admin だけ、をどこで止めるか。** routes の guard（`requireAdmin`）でも止められるが、それだと HTTP 以外の入口では素通りする。
   ルールは domain に置き、service で確かめた。guard は「画面ごと admin 専用」のような HTTP の都合のときに使う、と分けるのがよさそう
