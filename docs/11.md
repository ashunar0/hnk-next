# 設計の改善案と、パッケージ化の候補

レビューで出た提案のまとめ。レビューは GitHub 上のコードを読んだだけなので、実際に試して判断してほしい。

読んだのは `packages/hnk`（`src/index.ts`、`src/result.ts`、`lint.mjs`）と、`hono/api` の `deps.ts`、`errors.ts`、`middleware/auth.ts`、`modules/invoices/` の `domain.ts`、`service.ts`、`routes.ts`、`repo.d1.ts`、`commands/markPaid.ts`。読んでいる途中でリポジトリが更新されていて（`hnk/page`、`hnk/system`、共有 `shares`、範囲の `member` が入った）、`service.ts` と `domain.ts` は古い版を読んだ可能性がある。すでに直っているものは無視してほしい。

## 読んで良かったところ（変えないでほしい）

- `LAYERS` の許可表（ここに無いものは全部だめ）と、直し方まで出る lint のメッセージ
- `reachOf` / `InvoiceReach` で閲覧範囲を型にして、repo は `*Within` だけにする作り
- `System` を受け取る `markPaid`。routes は他 module の domain を import できないので、「システムとして呼べる」のは利用者のいない入口（webhook、cron、queue）だけに限られる
- `allowAnonymous`（何もしない関数）で、書き忘れと「公開したい」を分けて、grep で列挙できるようにしたこと

## 設計の改善案

### 1. 状態遷移を domain の表に集約する

`send`（draft → sent）は service に、`markPaid`（sent → paid）は commands に、それぞれ別のファイルで書かれていて、`isSendable` や `unpaidStatuses` とも別々になっている。「この請求書にどんな遷移があるか」を 1 か所で読めない。

```ts
export const invoiceTransitions = {
  send: { from: "draft", to: "sent" },
  markPaid: { from: "sent", to: "paid" },
} as const satisfies Record<string, { from: InvoiceStatus; to: InvoiceStatus }>;
```

- `repo.updateWithin(..., from)` に渡す値と、`isSendable` などの判定を、ここから取る
- 「条件付き更新 → 失敗なら原因を調べる」という同じ形が `send` と `markPaid` に出ていたので、遷移が増えても形が揃う
- `from` が複数になる場合（`unpaidStatuses` のようなもの）は、配列でもよい
- class の議論（`class-or-function.md`）で出た「状態遷移をモノの側に入れるか」の、関数版の答えにもなる

### 2. `errors.ts` が膨らみ始めている

`errors.ts` に、共通のもの（`Unauthorized`、`NotFound`、`Forbidden`）と、特定の module や webhook 専用のもの（`NotDraft`、`NotPayable`、`PaymentStarting`、`GatewayFailed`、`InvalidSignature`）が混ざっている。module が増えると、このファイルが肥大して、名前も衝突しやすくなる。

- 共通のものだけアプリの `errors.ts` に残し、固有のものは使う module の inbound 側に置けるようにする
- その場合、`httpError` のコードがアプリ全体で重複しないことを、lint かテストで保証する（同じコードに別のステータスが付くのを防ぐ）
- `LAYERS` の許可表も合わせて直す（routes が import できる範囲）

### 3. スキャフォールドの TODO を取りこぼせる

`repo.d1.ts` に `TODO: この表が何を保存するのか、1 行で書く` や、外部キーの `TODO` が残っていた。生成器かテンプレから出たように見える。

- 決まったマーカー（`TODO(hnk):` など）を lint で止める。埋め忘れのまま通る状態が書けなくなる
- 小ネタ: `repo.d1.ts` のモジュール上部の `const now = sql...` と、`listOverdueWithin(reach, now)` の引数 `now` が同名で影になっている。SQL の式のほうを別名にして、AI の取り違えを減らす

## パッケージとして提供する候補

### 4. `hnk/test`（一番効くと思う）

README の未決にもある、テストからログイン状態を作れない件。AI が自分で正しさを確かめるには、これが要る。

- `testApp({ viewer, deps })` で、任意の閲覧者と、差し替えた依存で app を作れるようにする
- service が宣言した repository の形に合わせた偽物は手書きになるので、放っておくと本物の D1 の repository とずれていく。**同じ契約テストを、偽物と D1 の両方に流す仕組み**を提供すると、ずれが書けなくなる

### 5. 文書をルールの定義から生成する

README が古くなる問題の根本対策。

- `LAYERS`、`KINDS`、`HINTS` を単一の真実にして、そこから `layers.md` を生成し、AGENTS.md や conventions に取り込む。ルールを変えれば文書も変わる
- あわせて `pnpm check` を 1 つ作る（tsc、oxlint、`format:check`、test を一括で回す）。AI に「これを通せ」と言うコマンドを 1 つに決める

### 6. route 側のページング

repo 側は `hnk/page` の `toPage` で済んでいる。クエリ（`cursor`、`limit`）と応答（`items`、`nextCursor`）のスキーマ、cursor のエンコード / デコードも `hnk/page` に寄せられるはず（すでにやっていたら無視してほしい）。

### 7. 保留: 範囲付きの読みの枠

`within`、`accessIn`、`invoicesWithin` は、今は invoices の中に手書きしてある。2 つ目の module で同じものを書くことになったら、「共通にしないと、範囲を付けずに読む書き方が書けてしまう」と言えるかで、共通化を判断する。今は 1 つしかないので、待ってよい。

## その他

- lint のルール自体のテスト（わざと違反を書いて、メッセージ付きで落ちることを確かめるもの）があるか確認する。メッセージが AI への指示になっているので、メッセージも含めてテストしておくと安全
- `lint.mjs` が 500 行を超えている。ルールごとにファイルを分けて、`LAYERS` の表を別ファイルにすると、読みやすく、5 の文書生成にも使いやすくなる

## 進め方（提案）

優先度の高い順に、次の順で進める。

1. 4（`hnk/test`）。他の変更を安全に進める土台になる
2. 5（文書の生成と `pnpm check`）。ルールが増えるほど効く
3. 1（状態遷移の表）。小さく試せて、class の議論にも効く
4. 2、3（`errors.ts` の整理と TODO の lint）
5. 6、7 は、2 つ目の module が育ってから判断する

## 結果（2026-10-10）

- 6（route のページング）は済んでいた（`hnk/page`、`pageQuery`、`pageResponse`）。4 の前半（テストから利用者を差し替える）も、`buildApp(makeDeps, authenticate)` と `appAs` で済んでいた
- 4 の後半（repo の偽物と D1 の両方に同じ契約テスト）は見送り。repo の偽物は作らず、本物のローカル D1 を使う方針（README の未決）なので、ずれる偽物が無い
- やった: `pnpm check`（typecheck、lint、format:check、test、hnk の lint テスト）、`migrations/meta` を prettier の対象外に、雛形の TODO と `now` の影（`nowMs` に改名）の修正、**lint ルールのテスト**（`packages/hnk/test/lint.test.mjs`。違反を書いたファイルを oxlint に通し、ルール名とメッセージの一部、指摘の数を固定する。文言を変える、ルールを切るのを検知することを確かめた）
- 待ち: 1（状態遷移の表。遷移が 2 つで失敗の扱いが違う。3 つ目が現れたら）、2（`errors.ts` の分割。固有のエラーを足す module が出たら）、7（範囲付きの読みの枠。読み手が 2 つ目になったら）
- 次: `lint.mjs` の分割（ルールごとのファイルと `LAYERS` の表）、5（`LAYERS` から文書を生成）。lint テストのカバー範囲は、今 7 ルール中 7 だが、各ルールの網羅は浅い（例: route-declares-auth の「2 個ある」「先頭に置く」）
