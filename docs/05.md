## 2. 指摘ごとの対応

### 3.1 箱の名前 → core / inbound / outbound

「モノ・入口・出口」の考え方はそのまま採用し、言葉はヘキサゴナルを実装するときの定番に揃えた。

| 側       | 何か                                                 | ファイル                     |
| -------- | ---------------------------------------------------- | ---------------------------- |
| core     | そのモノが何で、何ができるか。外を何も知らない       | domain, service, commands    |
| inbound  | 外から呼ばれる側。誰として呼ぶかを決めて core に渡す | routes, webhook, cron, queue |
| outbound | 外へ出ていく側。core が宣言した形を満たす            | repo, gateway, mailer, jobs  |

README の「出発点」と「育ち方」の表をこの言葉で書き直した。この分類は lint にもそのまま使っている（⑤）。

### 3.2 他 module の状態は問いで聞く → 採用

- reminders は invoices に `getRemindable(id, viewer, now)` を問い、自分で `status` を比べない。判定は invoices の domain の `isRemindable`。
  返す形から `status` が消えたので、`status: string` に型が落ちていた件も消えた
- 状態の集合を invoices の domain の定数にした（`billedStatuses = ["sent", "paid"]`、`unpaidStatuses = ["sent"]`）。
  ルールの関数（`isOverdue`、`isPayable`）と SQL（期限切れの WHERE、reports の集計）が同じ定数を使う。
  そのため、repo は他 module の domain の値（定数）を import してよいことにした
- 時間の条件のように定数で共有できないものは、**契約テスト**で揃えた（③）

### 3.3 「誰の権限で」の渡し方 → 判別共用体にした

```ts
export type User = { kind: "user"; id: string; role: Role }; // 認証から作られる
export type System = { kind: "system" }; // 利用者のいない inbound が渡すときだけ
export type Viewer = User | System;
```

- `system` はロールから外れた
- `create` は `User` しか受け取らない。システムは所有者になれない（型テストで確認）
- commands の `markPaid(system, id)` と payments の `receive(system, event)` はシステムの印を受け取る。
  webhook・cron・queue の 3 つとも、inbound が `systemViewer` を渡す形に揃った
- routes が `systemViewer` を import すると lint が止める（⑤）。commands を routes に渡さないのは、今まで通り deps が保証する

### 3.4 外への副作用と記録の順番 → 「先に記録 → 外へ → 結果で確定」に揃えた

| 場面           | 前                       | 後                                                                             |
| -------------- | ------------------------ | ------------------------------------------------------------------------------ |
| 支払いを始める | 決済画面を作る → 記録    | pending を記録 → 決済画面を作る → 識別子を結びつける。作れなければ失敗で閉じる |
| 督促メール     | 記録を見る → 送る → 記録 | 押さえる（claimed）→ 送る → 確定（sent）                                       |

- 冪等キーを渡すようにした。Stripe には `paymentId`、Resend には `reminder/{請求書}/{日付}`。
  Resend は `Idempotency-Key` を 24 時間保つ（確認済み）。督促の「1 日 1 通」とちょうど噛み合い、
  押さえたまま落ちても、再送で同じキーを使えば提供元が 1 通にまとめる。**督促は欠けも重複も起きない**
- 支払いは、画面を作った直後に落ちると識別子の無い pending が残る。利用者はまだ画面を受け取っていないので「欠けてもよい」と判断し、service のコメントに書いた
- Result と throw の基準を README に書いた: **呼び出し側が別の道に進める失敗は Result、進めない失敗は throw**

### 3.5 配線の循環 → 文書とスモークテスト

- README に「module の依存は一方向」と書き、今の向きを明記した（users ← invoices ← payments、invoices ← reminders、invoices と payments ← reports）
- deps の getter を全部 1 回ずつ組み上げるスモークテストを置いた（`test/deps.test.ts`）

### 3.6 HTTP 以外の入口の道具 → 後回し

必要なのは同意している。3.1 と 3.3 が決まり「inbound が誰として呼ぶか」の形が固まったので、作るなら今の形の上に乗せられる。
今は cron と queue が `api/index.ts` で `makeDeps(env)` を手で呼んでいる。

### 3.7 domain の入力スキーマの兆し → 記録だけ

画面の文言はフロントと共有するために意図して入れたもの。`z.coerce.date` は JSON の都合なので、
HTTP 用の入力型を分ける（育ち方の「中で割れる」）最初の合図として扱う。まだ割っていない。

## 3. 実行して確かめた（04 の 4「実行して確かめる」）

`@cloudflare/vitest-plugin` で、本物と同じマイグレーションを当てたローカルの D1 に対してテストを動かすようにした（`pnpm test`）。
テーブルの定義（各 module の `repo.d1.ts`）から drizzle-kit でマイグレーションを作っている。今は 11 本、全部通る。

| テスト               | 確かめていること                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------- |
| 一覧のページ送り     | 更新の新しい順に重複も抜けもなく辿れる。同じ時刻の 2 件がページの境目にまたがっても落ちない。状態で絞り込める |
| 期限切れの契約テスト | domain の `isOverdue` と repo の SQL に同じ固定データを通し、答えが一致する                                   |
| 月ごとの集計         | データの無い月は 0、下書きと失敗した支払いは数えない、member は見られない                                     |
| 配線のスモーク       | deps の getter が全部組み上がる                                                                               |
| HTTP                 | OpenAPI の文書が作れる（query の zod の transform を含む）、未ログインで 401                                  |
| 督促の順番           | 同じ日に 2 回届いても送るのは 1 回。メールに失敗したら押さえたまま残り、再送で同じ冪等キーで送り直す          |
| 支払いの順番         | 成功なら pending に識別子が結びつく。決済画面を作れなければ失敗で閉じる                                       |

テストが空振りしていないことも確かめた。期限切れの SQL を `<` から `<=` にわざと変えると、
契約テストが「ちょうど今が期限」の 1 件で落ちる。

つまずいた所（記録として）:

- 何も指定せずに入れると vitest 5 が入るが、プラグインは vitest 4 まで。4 に固定した
- pnpm 12 が esbuild と workerd のバイナリ取得を止めるので、`pnpm-workspace.yaml` の `allowBuilds` で許可した
- `cloudflare:workers` の `env` は `Cloudflare.Env` 型なので、`env.d.ts` でアプリの `Env` とつないだ

## 4. lint（03 で何度も出た「対象外」への対応）

04 は lint を扱わなかったが、03 の場面 3〜5 で一番大きな穴だったので、3.1 の分類を使って書き直した。

- module の中のファイルを、名前の頭（役割）で core / inbound / outbound に分ける。技術名は落とす（`webhook.stripe.ts` → webhook）
- **役割の分からないファイルは module の中に置けない**。新しい役割が黙って素通りしないようにするため
- 全部の役割を許可表に載せた

| 側       | 役割             | import してよいもの                                                                                                |
| -------- | ---------------- | ------------------------------------------------------------------------------------------------------------------ |
| core     | domain           | zod, 他 module の domain（型だけ）                                                                                 |
| core     | service          | hnk/result, domain, 他 module の domain（型だけ）                                                                  |
| core     | commands         | hnk/result, domain, service（型だけ）, 他 module の domain（型だけ）                                               |
| inbound  | routes           | hnk, zod, errors, middleware, domain                                                                               |
| inbound  | webhook          | routes と同じ ＋ 他 module の domain（systemViewer）                                                               |
| inbound  | cron / queue     | deps（型だけ）, domain（型だけ）, 他 module の domain（systemViewer）                                              |
| outbound | repo             | drizzle-orm, db（型だけ）, domain, service（型だけ）, 他 module の repo（join）, 他 module の domain（SQL の定数） |
| outbound | gateway / mailer | hnk/result, domain（型だけ）, service（型だけ）                                                                    |
| outbound | jobs             | domain（型だけ）, service（型だけ）                                                                                |

- routes 向けの規則（認証の指定、`reply` で返す、export は束 1 本、引数の中で await しない）は、HTTP の inbound（routes と webhook）全部にかける
- 向きの間違いには、側の組でヒントを出す（例: 「inbound は outbound を知らない。deps から core を受け取って呼ぶ」）

03 で 0 件で素通りした違反を書き直すと、8 件とも止まった（gateway・webhook・cron が repo を import、webhook で認証の指定なし、
webhook で `c.json`、routes が `systemViewer` を使う、commands が service の値を使う、役割の分からない `helpers.ts`）。
