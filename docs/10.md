# domain を class にするか、関数 + 型のままにするか

議論用のメモ。レビューは GitHub 上のコードを読んだだけなので、実際に試して判断してほしい。

## 背景

- 現状は、`domain.ts` が `type Invoice = {...}` と、それを受け取る関数（`canSend`, `isSendable`, `isRemindable`, `reachOf` など）。service も repository も「関数 + クロージャ」で、class はエラー（`HnkError extends HTTPException`）にしか使っていない
- 設計者は「モノ（What）」を中心に考える癖があり、class（インスタンス）が分かりやすいという感覚がある
- `this` の扱いが面倒なのは承知の上。迷わないなら class を採用したい、という気持ちがある

論点は「domain のモノを class にするか」。service や repository まで class にするかどうかは別の話で、ここでは扱わない（下の線引きを参照）。

## TS で class と関数を使い分ける理由（前提）

- **`this`**: class のメソッドは `this` に依存するので、関数として切り離して渡すと壊れる。例えば `deps.ts` の `getPayable: this.invoices.getPayable` のように、メソッドを関数として他に渡す書き方は、class だと `bind` かアロー関数のメソッドが要る。クロージャなら `this` が無いので、そのまま渡せる
- **隠蔽**: TS の `private` は型の上の約束で、実行時は丸見え（`#` なら本当に隠せる）。クロージャは中身が本当に触れない
- **ライブラリ側の都合**: `new Hono()` が class なのは、状態を持つ大きなオブジェクトで、継承して拡張される（`OpenAPIHono` が `Hono` を継承）から。使う側のアプリのコードが合わせる必要はない

## 案 C: domain のモノだけ class にする

モノは class、手順（service）は関数、と分ける。`domain.ts` が What、`service.ts` が How という今の切り方に、そのまま乗る。

```ts
export class Invoice {
  private constructor(private readonly props: InvoiceProps) {}
  static fromRow(row: InvoiceProps) {
    return new Invoice(row);
  }

  send(viewer: Viewer, now: Date): Result<Invoice, "FORBIDDEN" | "NOT_DRAFT"> {
    if (!canSend(viewer)) return err("FORBIDDEN");
    if (this.props.status !== "draft") return err("NOT_DRAFT");
    return ok(new Invoice({ ...this.props, status: "sent", updatedAt: now }));
  }
}
```

### 得るもの

- **正規の入口からしか作れない**。TS は構造的型付けなので、`type Invoice = {...}` は同じ形のオブジェクトリテラルが何でも通る。class に `private` なフィールドを持たせると、リテラルが代入できなくなり、`Invoice` は `fromRow` / `create` からしか作れない。ブランド型が `as` で破れる問題よりも一段強い
- **状態遷移のルールがモノの側に入る**。service は「取る → `invoice.send()` → 保存」くらいに薄くなる
- 「モノは class、手順は関数」と機械的に決まるので、AI が迷いにくい

### 払うもの

- **plain data ではなくなる**。`{...invoice}` で複製するとメソッドが落ちる。`JSON.stringify` やキューの payload にそのまま載せられない。応答は専用の型に詰め替える（conventions #31）ので、API の境界では困らない。ただし、キューやログに載せる箇所は注意が要る
- **更新の形を決める必要がある**。メソッドが新しいインスタンスを返すのか、自分を書き換えるのか。混ぜると事故るので、「新しいものを返す」に統一するのがよさそう。現在の `repo.updateWithin(id, reach, changes, from?)` の形とすり合わせが要る
- **repository の戻り値**: `Invoice` を返す箇所（`findWithin`, `insert` など）で、`fromRow` を通すことになる。conventions #37（保存の行の型とドメインの型を分けて変換する）と整合するので、むしろ位置づけは明確になる
- **`InvoiceInput`（zod の brand）は残る**。フロントと共有する入力のルールは、今のまま `domain.ts` に置く
- 変更量が大きくなる可能性がある（service と repo、テストの書き換え）

## 案 D: 今のまま（type + 関数）

- 利点: plain data で、コピーも JSON もそのまま。`this` の問題が無い。変更が要らない
- 欠点: 構造的型付けで、同じ形のリテラルが通る。モノの「正規の入口」を型だけでは強制できない（ブランドを足しても `as` で破れる）
- 補うなら: ブランドを作れる場所を 1 か所にして、`as` を lint で止める

## どちらでも守りたい線引き（lint で機械的に止める）

案 C にする場合:

- `class` を書いてよいのは `domain.ts` だけ（と、`Error` を継承するもの）
- service、repository、routes では `class` を書かない（今の関数 + クロージャのまま）
- `extends` は `Error` 系だけ
- コンストラクタは `private` にして、`fromRow` と `create` のような static ファクトリだけを入口にする
- domain のメソッドを切り離して渡さない（`items.filter((i) => i.isRemindable(now))` のようにメソッドを呼ぶ形で書く）

どちらの案でも共通: **同じ役割のファイルで class と関数を混ぜない**。迷うのは混ざるときだけ。

## 進め方（提案）

1. invoices の `domain.ts` だけを class にしてみる
2. service と repo がどれくらい変わるかを見る
3. 変更量や読みやすさを見て、続けるかやめるかを決める
4. 続けるなら、上の線引きを `lint.mjs` に足す（`class` の置き場所、`extends` の制限、private コンストラクタ）
5. 決めたことは conventions に残す（「モノは class、手順は関数」と、その理由）

## 議論したい点

- 「状態遷移のルールをモノの側に入れる」ところまでやるか、それとも `canSend` のような判定は今のまま関数にして、class は「正規の入口を強制する入れ物」だけに使うか
- 更新は「新しいインスタンスを返す」で統一してよいか
- `reachOf` や `InvoiceReach` のような、モノではなく「範囲」を表す型は、class にしない（type のまま）でよいか
- キューやログにモノを載せる場面で、plain data への変換をどこに置くか

## 結論（2026-10-10）: 見送り。今のまま（type + 関数）

あさひの判断: domain は class でなくてよい。アプリのコードに class を持ち込む理由は、今は無い。

- アプリのコード（`hono/api`）に class は 1 つも無い。class は hnk の中の `HnkError`（例外）だけで、`new Hono()` は `createRouter()` に包んである
- 案 C の得るもの（正規の入口の強制）は、偽造が困る権限（`User` と `System`）では `unique symbol` の印で済んでいる。`Invoice` は偽造して困る権限を載せていない
- 状態遷移をモノに入れても、競合を止めるのは SQL の `WHERE status = ...` なので、ルールが 2 か所になる点は今と変わらない
- 他 module との繋ぎは、使う側が構造的な形を宣言する方式。private を持つ class だと、getter などのボイラープレートが要る
- 「メソッドにするか関数にするか」の判断が新しく生まれ、AI が迷う場所が増える
- 10.md の前提の `getPayable: this.invoices.getPayable` は、deps.ts を const にしたので古い

きっかけが現れたら再検討する（例: 偽造されて困る権限を持つモノが domain に出てきたとき）。
