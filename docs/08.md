# deps.ts の組み立て方を見直す

レビューで出た指摘のまとめ。レビューは GitHub 上のコードを読んだだけなので、実際の挙動やテストは手元で確かめてから判断してほしい。

## 現状

`hono/api/deps.ts` の `makeDeps` は、module ごとの getter で service を組み立てている。

- `get invoices()` が呼ばれるたびに、service と repository を新しく作る
- `payments` や `reminders` の getter が、`this.invoices` のように他の getter を呼ぶ
- getter 同士が呼び合うので、依存が逆向きになると無限再帰になる。これは `test/deps.test.ts` で止めている
- `deps.ts` は `layer-imports` の対象外（`LAYERS` に `deps` が無い）

## 問題

Go の「`main` で手で組み立てる」（conventions #1, #2）と比べて、安全装置が 1 つ外れている。

Go が安全なのは、変数を宣言する前に使えないから。`a` が `b` を必要とするなら `b` を先に作るしかなく、循環は書けない。getter 方式にすると、この「宣言順 = 依存順」の保証が消えて、循環の検出をテストに頼ることになる。

あわせて、AI が間違えやすい点が増えている。

- getter 内の `this` の取り違え
- 呼ぶたびに作り直される（同じ service が複数できる）
- 循環が入ってもコンパイルは通り、実行時かテストで初めて分かる

これは Go と TS の言語機能の差ではなく、**ランタイムの差**から来ている。Go は起動時に 1 回組み立てるので遅延が要らない。Workers はリクエストごとに組み立てる必要があり（`provideDeps` のコメント参照）、使わない module まで作りたくないので、遅延を足した。その結果、宣言順の保証を失った。

TS でも `const` を順に並べれば、宣言前の参照を tsc が `Block-scoped variable used before its declaration` で止めてくれる。つまり、回収すべきなのは言語の差ではなく、遅延と引き換えに失ったもの。

## 案 A: 遅延をやめて、順番に const で組み立てる（まずこれを試す）

```ts
export const makeDeps = (env: AppEnv["Bindings"]) => {
  const db = wireDb(env.DB);

  const invoices = invoicesService(invoicesRepository(scopeTo(db, invoicesTable)));
  const payments = paymentsService(
    paymentsRepository(scopeTo(db, paymentsTable)),
    stripeGateway({ /* ... */ }),
    {
      getPayable: invoices.getPayable,
      markPaid: markPaid(invoicesRepository(scopeTo(db, invoicesTable))),
    },
  );
  const reminders = remindersService(/* ... */, invoices);
  const reports = reportsService(reportsRepository(db));

  return { invoices, payments, reminders, reports };
};
```

期待できること:

- 循環は tsc が止める。`deps.test.ts` に頼らなくてよくなる
- `this` が消える
- service は 1 リクエストにつき 1 つだけ作られる

確認してほしいこと:

1. **組み立てのコスト**。service と repository の生成はクロージャを返すだけのはずで、`db` の接続は `wireDb` の 1 回で済んでいるはず。実際に軽いか確かめる（`provideDeps` が handler で初めて deps を受け取るときに 1 回だけ呼ぶので、401 や `/openapi.json` では組み立てられない点は今のまま）
2. **env の検証**。gateway の生成で env を即座に検証していると、使わない module のキー（Stripe など）が無いだけで全リクエストが落ちる。これは「設定は起動時に 1 か所で検証する」（conventions #41）側に寄せれば、欠点ではなく利点になる。どこで検証するかを決める
3. 既存のテストが通ること。`deps.test.ts` は、循環を止める役割から「組み立てが通る」ことの確認に変えられるか見る

## 案 B: 遅延が本当に必要なら、lint で宣言順を回収する

案 A で組み立てが重いと数字で分かった場合だけ、getter を戻す。そのときは、コンパイラが止めてくれなくなった分を `hnk/lint` に足す。

- 「`deps.ts` の getter の中で `this.X` を参照していいのは、上に書いた getter だけ」というルール。宣言順を依存順として強制し、循環を書けなくする
- getter の結果は 1 回だけ作る（`??=` で保持する）形に統一する
- エラーメッセージは他のルールと同じく、直し方が分かる文にする（例: 「payments は reminders より前に書く。reminders に依存するなら reminders を上に移す」）

## 判断の基準

「遅延したい」は最適化の話で、安全性とは別の話。安全のほうを先に取る。遅延が要ると数字で分かったときに、その分だけ lint で補う。

ヘルパーを足す前に「それで何を失うか」を言えるか、というこのプロジェクトの基準にそのまま当てはまる。getter は「遅延」を得た代わりに「宣言順の保証」を失っている。この損得を、`deps.ts` のコメントか conventions に残しておく。

## あわせて決めたいこと

- `deps.ts` は何を import してもよい場所（Go の `main` と同じ）。ただ、配線は AI が一番間違えやすいので、書き方の型を conventions に書く。例: 他 module の repository を渡してよいのは commands だけ
- 案 A にした場合、`LAYERS` に `deps` を足して、`deps` が import できるものを表にするかどうか

## その他のレビューメモ（優先度は上の件より低い）

- **README が古い**。構成図が `features/invoices/route.ts` のままで、実装は `modules/invoices/routes.ts` と役割別のファイル。`contract/<feature>/model.ts` もいまは `domain.ts` にある。「失敗の番号衝突」も未決に残っているが、`errorResponses` がステータス単位でまとめて解決済み。AI が最初に読む場所なので、直すか `LAYERS` の表への案内だけにする
- **共通部品の置き場が無い**。`routes` が import できるのは hnk、zod、errors、middleware、domain だけで、`encodeCursor` / `cursorSchema` は routes.ts の中。他の module にも一覧が出ると置き場が無くなる。ページングのように「毎回手書きすると形が揺れるもの」は、hnk 側に置くか、共通部品の役割を決める
- **規約として決まっていない選択**: 作成が `201` でなく `200`、削除が `{ ok: true }` の `200`。失敗コードが全部 `errors.ts` に集まる設計だと、`NotDraft` のような特定 module の失敗が溜まって膨らみ、名前も衝突しそう（`errors.ts` は未確認）
- **ID が `string` のまま**。ブランド型にするなら、`as` で破れるので、ブランドを作れる場所を 1 か所にして `as` を lint で止めるところまでセットにする
- **conventions.md の hnk 側の列**は、`LAYERS` の表をそのまま書き出せばほぼ埋まる
- 新しい module（reminders や reports など）を AI に「invoices と同じ形で」書かせて、違う形になった箇所をルールの漏れとして拾う

## 結果（2026-10-10）

案 A を採用した。`deps.ts` を上から順の const にして、getter と `this` をやめた（invoices の repository も 1 つを共有）。

- 宣言の前に使うと `TS2448: Block-scoped variable used before its declaration` でコンパイルが通らない。わざと書いて確かめた
- 組み立ては関数を返すだけ（gateway・mailer・queue も設定を包むだけで、env の検証も接続もしない）なので、重さは測っていないが問題にならない見込み
- `test/deps.test.ts` は「循環を止める」から「組み上がる・同じ service は 1 つ」の確認に変えた
- 見送り: `LAYERS` に `deps` を足すこと（Go の main と同じく何でも import してよい場所）。env の検証を起動時に 1 か所でやること（検証が入るときに決める）
- 残り: ページングなどの共通部品の置き場、ID のブランド型、conventions.md の hnk 側の列は未着手
