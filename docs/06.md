## 4つの質問への答え

**1. 組織・共有は、2段構えがいいと思う**

- **組織(テナント)**: リクエスト中は変わらず小さいので、`User`に`orgId`を持たせて、入口で解決する。`reachOf`は純粋なまま、`{ kind: "org", orgId }`のようなデータを返す。memoの`TenantDb`が担っていた役を、`Reach`がデータの形で担う。
- **共有(行ごとの関係)**: 大きくて行ごとに違うので、Viewerには載せられない。`Reach`をデータのまま repo が解釈して(`owner = ? OR EXISTS(共有表)`)、**行と一緒に「どの関係で見えたか」(`access`)を返す**。`canEdit(viewer, invoice)`は、その事実を受け取る純粋関数に保つ。

範囲を非同期の「問い」にするのは避けたい。domainが純粋でなくなるし、一覧でN+1になる。

組織を入れると、一番の漏れの面は**他moduleのテーブルをSQLで直接読む所**になる。今の`reports`は`invoicesTable`をそのまま集計していて、範囲の条件が無い。組織を入れる時は、`reports`が`Reach`を受け取って、invoices が出す`within(reach)`を通す形にしたい。

**2. 副作用の判断は、督促は十分で、支払いに穴がある**

督促は、冪等キーで欠けも重複も防ぐ書き方で足りてる。ただし保証が効く範囲(「24時間以内の再送なら」)も、コメントに書いておくと誤読されない。

支払いの「欠けてもよい」という判断は、途中で落ちた場合には成り立つ。でも**二重に開始された場合**が漏れてる。`start`は呼ぶたびに新しい`pending`と新しい決済画面を作る(`paymentId`は毎回ランダムなので、Stripeの冪等キーも効かない)。利用者が2回押すか2タブで開くと、画面が2つ有効になる。両方で払われると、2つ目の`receive`は`markPaid`の「もう支払い済みならそのまま返す」を通って成功になり、**二重払いが「全部成功」で終わる**。冪等にしたことが、業務上の重複を隠してる。

「1つの請求書に進行中の支払いは1つ」を、payments の domain のルールにして、DBの部分ユニーク索引(`invoice_id`、`status='pending'`)でも守るのがいいと思う。2回目は既存の画面を再利用するか、前のを失効させる。(payments の repo は未読なので、すでに制約があるかもしれない。)

**3. lintの許可表は、今は緩めたままでいい**

- 他moduleのdomainの定数: 純粋なデータなので問題ない。
- 他moduleのrepoのimport: 他moduleのrepo関数は`Scope`が作れず呼べない。本当のリスクは呼び出しではなく、**他moduleのテーブルを直接読めること**。

組織・共有を入れる時に、他moduleに見せていい読みの部品(テーブルと`within`)を、`repo.d1.ts`から別のファイルに出して、foreignにはそこだけ許可する形を一緒に決めるのがおすすめ。「読むときは何も足さない」という方針は、テナントの話が入ると理由が変わる。

**4. HTTP以外の入口の道具は、4つだけ持たせたい**

- **deps の組み立て**を、呼び出しごとに1か所で行う。今は`index.ts`で`makeDeps(env)`を手で呼んでる。
- **`system`を渡すのは道具だけ**にする。cronやqueueのファイルは`systemViewer`をimportせず、受け取るだけにする。印を作る場所がhnkの中に1つになって、下の「印の抜け」も解ける。
- **ackと再試行をメッセージ単位**で決める(成功とSKIPPEDはack、再試行できる失敗はretry、想定外はthrow)。
- **`now`をイベントから渡す**(`scheduledTime`やメッセージの時刻)。今のcronは渡せてるので、キューにも揃える。

モジュールが`cron`や`queue`を公開して、`index.ts`の手配線を無くすのもここに含められる。スケジュールのDSLや再試行ポリシーの設定は、持たせなくていい。

## 04で言い足りなかった点

**印が型に無い**: `System`は`{ kind: "system" }`で、`User`も構造だけなので、**どのファイルでも`{ kind: "system" }`と書けば型を通る**。「routesが`systemViewer`をimportするとlintが止める」は、リテラルを書かれると素通りする。

```ts
declare const systemBrand: unique symbol;
export type System = { readonly kind: "system"; readonly [systemBrand]: true };
```

のように、印を型に持たせれば、リテラルでは書けなくなる(作れるのは`systemViewer`か明示的なキャストだけ)。`User`も同じで、認証を通った時だけ作れる印を付けたい。

小さい点として、`deps.ts`のコメントに`feature`と`hnk g feature`がまだ残ってる。それと、督促で`getRemindable`が失敗してSKIPPEDになった行が`claimed`のまま残る。「見送った」を表す状態があると、後から辿りやすい。
