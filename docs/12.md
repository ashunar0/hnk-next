## 輪の保証（deps.ts）

`deps.ts` は上から順に const で組み立てるので、相手を**そのまま渡す**所では、輪を書くと `tsc` が「宣言の前に使っている」で止める。
しかし、他の module の ID に印を付けて渡す所は、`(id, viewer) => invoices.getPayable(invoiceId(id), viewer)` のように関数で包むので、
遅延評価になり、輪があっても `tsc` は止めない。README の主張はこの形と矛盾していた。

選択肢は 2 つだった。

- (a) 包む書き方を残し、README の主張を外す
- (b) 印を service の中で付けて、直接渡す（service が他 module の domain を値で import できるようにする）

(a) を選んだ。理由: 輪はまだ一度も起きていない。包んでいる所が、そのまま module の境目の一覧として grep できる。
(b) は変更が大きい割に、得るのは輪の保証だけ。輪が起きる兆しが出たら、`deps.ts` の依存を調べるテストを足す。

## 未決のまま（判断待ち）

- lint `no-await-in-call-arguments`: 「無いと、どんな間違いが書けてしまうか」に答えられない見た目のルール。削除の候補
- lint `route-exports-only-the-router`: `layer-imports` が、他 module からの routes の import を既に止めている。残る穴は `api/index.ts` だけ

- `Reach` を `users/domain` に移す。payments と reports の repo が `invoices/domain` から借りているのは事実。ただし `member`（自分のものと共有されたもの）の意味は請求書の共有に依存する
- 「ミスしても AI 自身が気づいて直せる」の実験。lint のテストの違反ファイルを渡して、`pnpm check` を通させ、何回で正しい直し方に届くかを数す。狙いのこちら側は、まだ一度も測っていない
