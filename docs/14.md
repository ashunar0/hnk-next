## 2. 「輪はコンパイルが通らない」は成り立っていない

README に「deps.ts は上から順に const で組み立てる。依存する相手を先に書かないと tsc が止めるので、輪はコンパイルが通らない」とある。手元で確かめた：

```ts
const mkA = (dep: { f: (x: string) => number }) => ({
  g: (x: string) => dep.f(x) + 1,
});
const mkB = (dep: { g: (x: string) => number }) => ({
  f: (x: string) => dep.g(x) + 1,
});

// 直接渡す: tsc が TS2448 で止める
export const a1 = mkA(b1);
export const b1 = mkB(a1);

// アロー経由: 通る。実行時も遅延評価なので動く
export const a2 = mkA({ f: (x) => b2.f(x) });
export const b2 = mkB({ g: (x) => a2.g(x) });
```

deps.ts は ID の印を付けるために `getPayable: (id, viewer) => invoices.getPayable(invoiceId(id), viewer)` とアロー経由で繋いでいる。これは後者の形なので、輪があっても tsc は何も言わない。印のラッパーを入れた時点で、輪の保証は失われている。

### 直し方の案: 印を deps.ts で付けるのをやめる

原因は `service` の許可表が `"foreign:domain": "type"` なこと。これを `"value"` にする（repo にはもう許している。domain は外を何も知らないので、値で借りても矢印は変わらない）。

- payments の service が `invoiceId: InvoiceId` で宣言でき、deps.ts は `getPayable: invoices.getPayable` と直接渡せる
- ラッパーが消え、輪の保証が戻り、REVIEW.md の問い 5「ID の印を deps.ts で付ける形は読む人に分かるか」が問い自体消える
- README の未決「共有の相手の利用者 ID は素の `string` のまま」も同じ根。routes に `foreign:domain` の値を許せば解ける

## 3. Reach の置き場所

`InvoiceReach` / `reachOf` は invoices の domain にあるが、中身は Viewer だけから決まる「閲覧者の範囲」で、payments の repo も reports の repo も契約テストも、テナントの線としてこれを使っている。

- `Reach` と `reachOf` は `users/domain` に移す。`InvoiceAccess` と `accessIn` は invoices に残す
- repo の `"foreign:domain": "value"` の例外（「集計の SQL で定数を使う」）の半分が要らなくなる
- `payments/repo.d1.ts` の import が「users から範囲、invoices から入口」と、意味どおりに並ぶ

## 4. module をまたぐ書き込みに、1 行足す

「1 回の書き込みで変えるのは 1 つの module だけ、再送でやり直す」が成り立つのは、呼び出し元に再送があるときだけ。今うまく行っているのは、module をまたぐ書き込み（`markPaid`）が webhook からしか呼ばれないから。routes（利用者の HTTP）から 2 つの module に書く操作を作った瞬間、途中で落ちたら誰もやり直さない。

足す決まり: **module をまたぐ書き込みは、再送のある inbound（webhook / queue / cron）からだけ。routes からは 1 module だけ**。今のコードは満たしているが、明文化されていないので AI は守れない。

## 5. 検証: 「ミスしても AI 自身が直せる」を測っていない

狙いの 2 つ目は、赤線の位置と lint の文言を設計対象にするほど重く置かれているのに、効いているかの実験が無い。

提案: わざと違反を仕込んだ状態（宣言の無い route に `reply.failure("NOT_DRAFT")`、foreign table を `from` に、`as InvoiceId`、など 10 個ほど）を渡して「`pnpm check` を通して」とだけ言い、何回で・正しい方向で直るかを数える。lint のテストの違反ファイルがそのまま素材になる。n=1 でも「この文言だと別の方向に直した」が拾えるので、同じ依頼を繰り返す実験より情報量が多い。

## 6. 美しさ: 簡潔さの基準を 1 本足す

### 綺麗な所（変えない）

- `within(reach)` が WHERE の断片になり、`invoicesWithin` が副問い合わせに包み、`paymentsWithin` がそれを join する。範囲が関数合成で伝播し、契約テストが export 名で自動で拾う。ルールが 1 か所にあって、他は全部そこを通る、が SQL の構造そのもので表現されている
- `scopeTo`。「読みは越境してよく、書きは自分の表だけ」の非対称が 4 行で型になっている。`ReadDb = Pick<Db, "select">` も最小で正確
- `updateWithin(id, reach, changes, from?)`。確認と書き込みを 1 文に畳み、状態遷移の競合まで同じ文に入れている。`markPaid` の「まず書いて、書けなければ診断する」も、冪等性が自然に出ている
- service.ts の上に repo の形、下に手順。読む順番と依存の向きが一致している
- domain.ts が仕様書のように読める。`isRemindable = isOverdue` で「督促してよい＝期限切れ」を言い切っている

これらは短くて、賢くなくて、全部が同じ形で通る。簡潔で、かつ整列している。

### 基準

「簡潔」の中に 2 つ混ざっている。

- **概念を減らす簡潔**: 覚えることが少ない、場所が少ない、同じ言葉が層をまたいで使える。整列の材料になる
- **文字を減らす簡潔**: 型の技や言語の小技で打つ量を減らす。必ず 1 か所だけ形が違う所を作るので、整列を崩す

上の「惜しい所」は全部後者で、直し方は「技を捨てて概念を減らす」方向に揃う。`.endpoint` のチェーンはスプレッドを消すと同時に `.openapi` の語彙も消す。`reply.ok` / `reply.err` は関数オブジェクトの技を消すと同時に語彙を 1 組にする。hnk の分割はファイルを増やすが、許可表との対応が生まれて覚えることは減る。

「作るヘルパーの基準」に 1 本足す: **それは概念を減らしているか、文字を減らしているか**。概念を減らすものは取る。文字を減らすだけのものは、整列を 1 か所でも崩すなら捨てる。

## 7. 問いへの答え（残り）

- **Q1 育ち方**: 4 つのきっかけのうち 3 つは事実で決まる。「1 つのファイルが 2 つ目の理由で変わり始めた」だけは人の感覚。正直にそう書いておけばいい。無理に機械化すると vision.md の「見た目から規約を考え始めるループ」に戻る
- **Q2 失敗**: 二重ではない。service の `"NOT_FOUND"` と `errors.ts` の `NotFound` は文字列で結ばれているだけで、service は番号を知らない。service に失敗コードを足すと `reply.failure(result.error)` に赤線が出るのが「処理を飛ばすと型エラー」の実体。guard の自動宣言は、ファイルに無いものが OpenAPI に出る唯一の場所だが、`guard([Unauthorized], ...)` に飛べば追えるので許容範囲
- **Q3 zod**: zod は domain で入力ルールをフロントと共有する時点で前提。zod-openapi が本当の結合で、`createEndpoint` の中に閉じている。defineHandler を待つ理由は無い
- **Q6 Reach**: 穴というより置き場所（上の 3）。「競合を domain の 1 か所に取った」は妥当
- **Q7 domain の class**: 見送りで正しい
- **Q8 lint**: 6 本が適正（上の 1）。文言の固定は良い。ただし `route-declares-auth.mjs` のコメントに `authUserId` が残っている（今は `authViewer`）。固定した文言のそばに古い名前があると、AI はそれも信じる
