## 1. 結論

指摘を受けて、構成をほぼ作り直した。中心にしたのは「要素が多くて、何がいつ出てくるのかが整理されていない」という問題。
元の hnk-next は、育った後の形（presenter、table、contract など）を最初から全部置いていて、どれが何のためにあるのかが読めなかった。

今の形は、元の案（1.1）の名前に寄せて、次の 4 ファイルから始める。

```
api/modules/invoices/
├─ domain.ts      モノ（What）: 型・ルール。import は zod だけ
├─ service.ts     モノ（How）: 手順と、手順が必要とする保存の形の宣言
├─ routes.ts      公開: HTTP の入出力の形、モノ → 応答の変換、route
└─ repo.d1.ts     保存: テーブル、D1 での実装、行 → モノの詰め替え
```

```
  routes ──────→ domain ←────── repo.d1
                   ↑               │
                service ←──────────┘ （service が宣言した保存の形を、型だけ借りて満たす）
```

矢印は全部 domain に向かう。routes は service を import せず、deps から受け取る。

## 2. 構成の考え方

### 2.1 関心事は 3 つ

Go（invoice / httpapi / sqlite）も Rails（MVC）も、扱う関心事は「それは何か」「どう外に見せるか」「どう保存するか」の 3 つ。
hnk-next はこれを技術的な役割で 6〜8 個に切り刻み、全部を横並びにしていたので、多く見えていた。

今はこの 3 つを箱として、モノの箱だけ What（domain）と How（service）の 2 ファイルにしている。
手順はどの module にも毎回あるので、最初から分けている。

### 2.2 育ち方

最初に置くのは「どの module にも毎回あるもの」だけ。規模で出てくるものは、最初からある前提にしない。
育つのは「2 つ目が現れたとき」だけで、動きは 3 種類。

| 動き | きっかけ | 足すもの |
| --- | --- | --- |
| 横に増える | 2 つ目の入口 | `cron.ts`、`queue.ts`（routes.ts の隣） |
| 横に増える | 2 つ目の保存先 | `files.r2.ts` など。必要な形は service で宣言する |
| 中で割れる | 1 つのファイルが 2 つ目の理由で変わり始めた | 同じ箱の中で分ける（service.ts → ports.ts、routes.ts → schema.ts など）。矢印は変わらない |
| 上に載る | 2 つ目の module が触りにくる | `index.ts`（公開口）。他の module はここからだけ触る |
| 上に載る | 1 回の操作で 2 つの module に書く | `usecases/` |

1.1 の 7 ファイル（domain, ports, schema, routes, repo.pg, index, test）は「育ちきった後の姿」として、全部この表のどこかに収まる。
アダプターのファイル名には技術名を付ける（`repo.d1.ts`）。差し替えられる外との接点だと、名前で分かるようにするため。

### 2.3 名前

- フォルダは `modules/`。「境界を持ったまとまり」で、Go の package に近く、1.1 の `index.ts`（公開口）とも噛み合う
- `features/` は「機能」で、複数のモノにまたがる操作（usecases の側）の言葉なので使わない
- `domains/` は、1 つのモノには大きすぎる言葉で、`domains/invoices/domain.ts` と重なるので使わない

## 3. 01.md の論点への回答

**論点 A: domain と zod の関係** → domain は zod を使ってよい、と決めた

- ルールを zod で 1 か所に書き、フロントのフォームとも共有する。自前の検査を書くのは割に合わない
- domain が import できるのは zod だけ（lint で止める）
- 入力のスキーマに `.brand<"InvoiceInput">()` を付けた。service は印付きの型しか受け取らないので、cron など HTTP 以外の入口から検査を飛ばして呼ぶと型エラーになる（`service.typetest.ts` で確認）。routes は zod-openapi が検査した値をそのまま渡すので、書き足すものは無い
- Go 版は service の中で `Validate()` を呼んで実行時に止めている。hnk では同じことを型で止める

**論点 B: 依存の向きがファイル名の約束止まり** → 許可表を lint にした

`hnk/lint` に `layer-imports` を追加した。表に無い import は全部止める。相対 import も tsconfig の paths 経由も同じように解決する。
型だけ借りる相手には `import type` を求める。テストのファイル（`*.test.ts`、`*.typetest.ts`）は対象外。

| 役割 | import してよいもの |
| --- | --- |
| domain | zod |
| service | hnk/result, domain（型だけ） |
| routes | hnk, zod, errors, middleware, domain |
| repo | drizzle-orm, db（型だけ）, domain（型だけ）, service（型だけ）, 他 module の repo（join のため） |

違反のメッセージには「何がだめか・どうすればいいか・何なら import してよいか」を入れた。例:

```
service が repo を import している。必要な保存の形は service に type で宣言し、repo がそれを満たす。
service が import してよいのは hnk/result, domain（型だけ）
```

似たことをしていた既存のルール 3 つ（no-foreign-repository など）と、no-restricted-imports の重複は、このルールに吸収して消した。

**論点 C: usecases/ の設計** → まだ作らない

「1 回の操作で 2 つの module に書くとき」に足す、と育ち方の表に位置づけた。module はまだ 1 つしかないので、中身は未設計。
lint のメッセージは、他 module の service を触ろうとしたら usecases/ を案内する。

**論点 D: service のデータ型が DB の行そのもの** → モノの型を domain に置き、行は詰め替える形にした

- `Invoice` は domain が宣言する。repo.d1 は行を `toInvoice` で詰め替えて返す（Go 版と同じ）
- 行の型は repo.d1.ts の外に出ないので、「DB の行をそのまま応答に返せる」穴も塞がった
- 書き換えてよい値は domain の `InvoiceChanges`（title / body / updatedAt）に絞った。`id` や `ownerId` は型の上で書き換えられない

## 4. その他の指摘への対応

| 指摘 | 対応 |
| --- | --- |
| update / delete が「確認 → 書き込み」の 3 手 | 所有者の条件を WHERE に入れ、`updateOwned` / `deleteOwned` の 1 文にした。`.returning()` で結果を受ける |
| get は NOT_FOUND、update / delete は NOT_OWNER で不統一 | 全部 NOT_FOUND に揃えた。NOT_OWNER は削除 |
| service が hnk 本体を import している（間接的に hono に依存） | `Result` を `hnk/result` に切り出し、service はそこからだけ import する |
| lint が相対 import しか解決しない | `layer-imports` で tsconfig の paths も解決するようにした |
| `contract` の語が曖昧 | `contract/` 自体を無くした。ルールは domain、HTTP の形は routes |

## 5. まだやっていないこと

- 時刻と ID の注入（service が `new Date()` と `crypto.randomUUID()` を直接呼んでいる）。テストで困ってから足す
- テナント分離（RLS）。D1 には RLS が無く、hnk はプラットフォームに縛らない方針。所有者の境界は WHERE で守る
- 同じステータスの失敗が 2 つあると片方が消える問題
- `no-module-scope-state` の見逃し（`const x = []` など）
- `fail`（throw）と `reply.failure`（return）の名前が似すぎている問題
- `cron.ts` など、許可表に無い役割のファイルは lint の対象外
- Go 版を今の形に揃えること（Go 版はまだ NOT_OWNER を返す）

## 6. 聞きたいこと

1. 「育ち方」の表（2 つ目が現れたときだけ、3 種類の動き）に、抜けや無理はないか
2. repo が他 module の repo を import できる（join のためにテーブルを借りる）形は妥当か。相手の repository 関数まで呼べてしまう。index.ts（公開口）ができるまでの暫定でよいか
3. routes が domain の入力スキーマをそのまま HTTP の受け取る形に使っている。Go 版のように HTTP 用の request の型を別に作って詰め替えるべきか。それとも、ずれが出てから分ける（中で割れる）でよいか
4. D1 には対話的なトランザクションが無い。usecases/ を作るとき、`batch` を前提にした形をどう設計するのがよいか
