## 3. 設計として詰めたいところ (重要順)

### 3.1 箱の名前が実態とずれている

3 つの箱は「モノ・公開・保存」だが、ファイルは 11 種類になった
(domain、service、routes、repo.d1、gateway.stripe、mailer.resend、jobs.queues、webhook.stripe、cron、queue、commands)。
整理すると実態は次の 3 つ。

| 箱 | 中身 |
|---|---|
| モノ | domain, service, commands |
| **入口** (呼ばれる側) | routes, webhook, cron, queue |
| **出口** (外に出る側) | repo, gateway, mailer, jobs |

- 「公開」では cron が説明できない。「保存」では Stripe やメールが入らない
- 育ち方の表は「入口」「保存先」と書いているのに、2.1 の関心事の説明だけ古い言葉のまま
- 「`queue.ts` と `jobs.queues.ts` が紛らわしい」(場面 5) も、入口と出口と呼べば解ける

### 3.2 他 module の状態の意味を、読んで自分で判定している箇所がある

- 良い例: payments は invoices に `getPayable` と**問い**を投げ、答えだけ受け取る
- 漏れている例:
  - reminders は `status !== "sent"` と文字列で比べている (しかも `OverdueInvoices.get` の型が `status: string` に落ちている)
  - reports は `inArray(invoicesTable.status, ["sent", "paid"])` と SQL に直書きしている

提案するルールの言葉:

> 他 module の状態の意味は、問いで聞く。値を読んで自分で判定しない。

SQL でまたぐ集計は、次のように揃える。

- 状態の集合は domain の定数にして、SQL も同じ定数を使う
- 時間条件のように共有できないルールは、同じ固定データを「domain の関数」と「SQL」の両方に通して、結果が一致するかを確かめる**契約テスト**で揃える

(場面 6 の引っかかり 1「同じルールを domain の関数と SQL の 2 か所に書いている」の答えになる)

### 3.3 「誰の権限で」の渡し方が 2 種類ある

- cron / queue: `systemViewer` を作って service に渡す (範囲の確認を通る)
- webhook: 閲覧者を取らない `markPaid` を呼ぶ (`all` を直書き)

システムの権限が、値と関数の形の 2 通りで表されている。しかも `system` が Role の 1 つとして
`reachOf` に並んでいるので、ロールを文字列で扱う入口で紛れ込む余地がある。

提案:

- Viewer を「利用者」と「システム」の 2 種類 (判別共用体) に分ける
- システムは入口 (cron / queue / webhook) だけが作れる形にする
- commands も同じ「システムの印」を受け取る形に揃える (`markPaid(system, id)` のように)
- routes から呼べないことの保証は、今まで通り deps が routes に渡さないことに頼る

### 3.4 「外への副作用と記録」の順番を、毎回人が決めている

場面 3 (決済画面 → 記録)、場面 5 (メール → 記録)、場面 4 (何度やっても同じ結果) で同じ問題が 3 回出ている。
方針として固めるなら:

- 先に記録 (pending や claim) を書く → 外へ出す → 結果で状態を確定
- 外が冪等キーを受けるなら使う (Stripe は paymentId を渡している。メールは提供元次第なので要確認)
- 「重複してもよい」か「欠けてもよい」かは、業務の判断として service に明記する

外部の失敗を `Result` にするか `throw` にするか (場面 3 引っかかり 5) の基準案:

> 呼び出し側が別の道に進める失敗 (再試行・案内・代替) は `Result`。進めない失敗は `throw`。

### 3.5 配線の循環が、どこにも映らない

module 同士は構造でつながるので、import の循環に出てこない。
deps.ts の getter が互いの getter を呼ぶ形 (`this.invoices` を payments に渡す、など) では、
invoices が payments を必要とした日に、実行時に無限再帰になる。

- module の依存は一方向 (invoices ← payments ← …) と決めて、文書にする
- 全 getter を 1 回ずつ読むスモークテストを 1 本置く (一番安い)

### 3.6 HTTP 以外の入口には、hnk の保証が無い

`createEndpoint` は deps の受け渡し、応答の型、認証の宣言を保証する。
cron / queue / webhook は index.ts で `makeDeps(env)` を手で呼んで自分で組み立てている。
入口の半分に型の保証が無い状態になっている。

- `createCron` / `createConsumer` のような対の道具があると、「システムとして呼ぶ」「失敗したら再試行か ack か」が 1 か所に集まる

### 3.7 小さい兆し

domain の入力スキーマに `z.coerce.date` (JSON の都合) や日本語の画面文言が入ってきた。
場面 2 の頃に挙がった「HTTP 用の入力型を分ける合図」が、静かに出始めている。
