# AI に、壊れたコードを直させた実験

作成日: 2026-10-10

REVIEW.md の狙いの 2 つ目「ミスしても、AI 自身が気づいて直せる」を測る。これまでの実験（docs/09.md）は 1 つ目（同じ形になるか）だけだった。

## 条件

- 渡したもの: 本物のアプリに違反を 12 個仕込んだコピー（ブランチ `exp/fix-5`）。README と docs は取り除いてある。頼んだのは「`pnpm check` を通して」だけ。`packages/hnk` と `.oxlintrc.json` は変えない、ルールは緩めない、commit しない
- 相手: Sonnet のエージェント 1 回（約 1.5 分、約 7 万トークン）
- 仕込んだ違反は、仕込んだ時点で全部検出されることを確かめた
- 結果は、仕込む前（baseline）との差分で確認した。アプリのコードは baseline と一致し、`pnpm check` は通った（テスト 43 件）

## 結果

12 個とも、意図した直し方に着いた。迂回（suppress コメント、`any`、ルールを緩める、テストを消す）は無かった。`pnpm check` の実行は 5 回。

## 分かったこと

- **lint の文言は、案内どおりに直せた**。lint のメッセージを読むだけで 1 回で直せたものが多い（1, 2, 6, 10, 11, 12）
- **文言が誤った方向に案内した例が 1 つあった（#5）**。`no-id-cast` は「domain の作る関数 `invoiceId(value)` で付ける」と案内する。しかし service は他 module の domain の値を import できない。案内どおりに直すと、別の lint（`layer-imports`）で落ちた。その後、型を変える方向に進み、広がったので戻し、最終的に cast を消した。正解は「service では付けず、`deps.ts` に任せる」だが、メッセージにはそれが無い
- **型エラーの赤線が、原因から離れる所がある（#3, #4）**。`'"authViewer"' is not assignable to parameter of type 'never'` は、`middleware` に `requireAuth` が無いせいなのに、赤線は `c.get("authViewer")` に出る。`'"FORBIDDEN" | "NOT_FOUND"' ... 'never'` も同じで、直す場所は上の `responses`。`never` が「この route が宣言していない失敗」を意味することは、文言から読めない。エージェントは周りのコードから推測して直した
- **検査済みの印の型エラーは、意図を言わない（#8）**。`Property '[$brand]' is missing` は、「`.parse()` を通した値でないと渡せない」とは言わない。エージェントは `service.typetest.ts` を読んで意図に気づいた
- **typecheck が落ちると lint まで進まない**。lint の指摘は 2 回目まで見えず、一度に直せる量が分からなかった。5 回のうち 2 回は、これで増えた

## 割り引いて読む所

- 1 回だけ。Sonnet だけ。コードを自由に読めた（`service.typetest.ts` などが手がかりになった）
- **仕込んだ違反のうち、#6、#7、#11、#12 は使われていないコードだった**。消すだけで直るので、「メッセージが本当の直し方を教えたか」は測れていない。使われている違反（実際に呼ばれている所）で試す必要がある
- #10、#11 の lint は、1 回で正しく直せた。ただし、使われていない `export` や、1 行の `await` で、直すのが易しい例だった。この結果だけでは、2 本を削るか残すかは決まらない

## 直したもの・直す候補

直した（2026-10-10）:

1. `no-id-cast` の文言に、「service など他 module の domain の値を import できない所では付けず、素の string のまま渡して、`deps.ts` で印を付ける」を足した
2. `pnpm check` を `hono/scripts/check.mjs` にして、途中で落ちても最後まで回し、失敗を一覧で出すようにした（型と lint の失敗が 1 回で両方見える）

3. `reply.failure` の `never`: 失敗を 1 つも宣言していない route では、引数の型を「この route には、手で書いた失敗の宣言が無い。responses に ...errorResponses(NotFound など) を足す」という文言の型にした（`api/reply.typetest.ts`）。一部だけ宣言している route は、宣言してあるコードが出る（元から）

まだ直していない:

3'. `authViewer` の `never`（`requireAuth` を書き忘れたとき）: Hono の `c.get` の型なので、hnk からは文言を差し替えられない。lint の `route-declares-auth` が「`middleware: [requireAuth]` か、公開なら `[allowAnonymous]` を置く」と案内する。`pnpm check` が型と lint を両方出すようになったので、この案内が見える 4. 検査済みの印の型エラーに、`.parse()` を案内する手段があるか調べる（TS の型エラー文言なので、できる範囲は小さい）5. 使われているコードに違反を仕込んだ、2 回目の実験

## 2 回目（使われているコードに違反を仕込んだ）

前回は 4 個が使われていないコードで、消すだけで直った。今回は 12 個とも**使われているコード**に入れた（ブランチ `exp/fix-6`）。条件は同じ（文書なし、「`pnpm check` を通して」だけ、Sonnet 1 回、約 1.2 分、約 7 万トークン）。仕込んだ違反は、全部検出されることを確かめた。

仕込んだもの: `c.json`、service が errors を throw、`send` の失敗の宣言を消す、reports の認証を消す、payments の `as InvoiceId`、reports service のモジュール先頭の `Map`（キャッシュとして実際に使う）、reports repo が表を直接読む、引数の中の `await`、routes の余計な `export`、domain が `Result` を返して service が使う、`share` の引数の取り違え、`markPaid` に `"all"`。

結果: 12 個とも意図した直し方。迂回なし。アプリのコードは baseline と一致し、`pnpm check` は通った（テスト 41 件）。**`pnpm check` の実行は 2 回**（前回は 5 回）。

- **直した 2 点が効いた**: `pnpm check` が型と lint を一度に出すようになり、実行回数が 5 回から 2 回に減った。`no-id-cast` の文言を直した後は、`as InvoiceId` を 1 回で消せた（前回は 3 回）
- **`reply.failure` の新しい文言は読めた**。ただし `rpc.typetest.ts` の赤線は、原因（`invoices/routes.ts` の宣言漏れ）と別のファイルのテスト側を指す。エージェントは、同じ原因の `routes.ts:199` の文言のほうを手がかりにした
- **`authViewer` の `never` は、文言からは `requireAuth` の書き忘れと結びつかない**（前回と同じ）。lint の `route-declares-auth` で初めて原因が分かった
- **テストが落ちる形で現れた違反**: `share` の引数の取り違えは、実行時の `FOREIGN KEY constraint failed` として出る。文言だけでは、スキーマの問題に見える（型エラー側が手がかり）
- **集計キャッシュの違反は、本物のバグを含んでいた**。キーが組織を区別していないので、別の組織の集計が漏れて tenant のテストが落ちた（期待 1000、実際 8000）。同時に表の直読みも範囲を絞っていなかった。2 つの原因が重なっていて、片方の文言では片方しか見えない。**テナントの線のテストが、型と lint で止まらない漏れを捕まえた**
- **lint 2 本（`no-await-in-call-arguments`、`route-exports-only-the-router`）は、どちらも 1 回で正しく直せた**。メッセージで足りた。ただし、これで「止める価値がある」ことは言えない。どちらも、直さなくても動く違反だった

割り引く所: 1 回だけ。Sonnet だけ。違反の組み合わせは私が選んだもの。
