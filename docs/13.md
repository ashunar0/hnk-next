# AI に、壊れたコードを直させた実験

作成日: 2026-10-10

REVIEW.md の狙いの 2 つ目「ミスしても、AI 自身が気づいて直せる」を測る。これまでの実験（docs/09.md）は 1 つ目（同じ形になるか）だけだった。

## 条件

- 渡したもの: 本物のアプリに違反を 12 個仕込んだコピー（ブランチ `exp/fix-5`）。README と docs は取り除いてある。頼んだのは「`pnpm check` を通して」だけ。`packages/hnk` と `.oxlintrc.json` は変えない、ルールは緩めない、commit しない
- 相手: Sonnet のエージェント 1 回（約 1.5 分、約 7 万トークン）
- 仕込んだ違反は、仕込んだ時点で全部検出されることを確かめた
- 結果は、仕込む前（baseline）との差分で確認した。アプリのコードは baseline と一致し、`pnpm check` は通った（テスト 43 件）

## 結果

12 個とも、意図した直し方に着いた。迂回（suppress コメント、`any`、ルールを緩める、テストを消す）は無かった。`pnpm check` の実行は 5 回。

| #   | 違反                                   | 検出      | 直し方                                             |
| --- | -------------------------------------- | --------- | -------------------------------------------------- |
| 1   | `c.json(...)` で返す                   | lint      | `reply(200, ...)`                                  |
| 2   | service が errors を import して throw | lint      | `err("NOT_FOUND")` を返す                          |
| 3   | 失敗の宣言が無いのに `reply.failure`   | 型        | `errorResponses(NotFound, Forbidden)` を足す       |
| 4   | 認証の指定が無い                       | lint と型 | `requireAuth` を足す（匿名を許す側に倒さなかった） |
| 5   | `as InvoiceId`                         | lint      | cast を消して、素のまま渡す（3 回かかった）        |
| 6   | モジュール先頭の `let`                 | lint      | 消す                                               |
| 7   | 他 module の表を直接読む               | lint      | 関数ごと消す（使われていなかったため）             |
| 8   | 検査を通さず `create`                  | 型        | `invoiceInputSchema.parse`                         |
| 9   | `share` の引数の順が逆                 | 型        | 順序を直す                                         |
| 10  | 引数の中で `await`                     | lint      | 変数に受ける                                       |
| 11  | routes が余計に export                 | lint      | `export` を外す                                    |
| 12  | domain が service を import            | lint      | import を消す                                      |

## 分かったこと

- **lint の文言は、案内どおりに直せた**。lint のメッセージを読むだけで 1 回で直せたものが多い（1, 2, 6, 10, 11, 12）
- **文言が誤った方向に案内した例が 1 つあった（#5）**。`no-id-cast` は「domain の作る関数 `invoiceId(value)` で付ける」と案内する。しかし service は他 module の domain の値を import できない。案内どおりに直すと、別の lint（`layer-imports`）で落ちた。その後、型を変える方向に進み、広がったので戻し、最終的に cast を消した。正解は「service では付けず、`deps.ts` に任せる」だが、メッセージにはそれが無い
- **型エラーの赤線が、原因から離れる所がある（#3, #4）**。`'"authViewer"' is not assignable to parameter of type 'never'` は、`middleware` に `requireAuth` が無いせいなのに、赤線は `c.get("authViewer")` に出る。`'"FORBIDDEN" | "NOT_FOUND"' ... 'never'` も同じで、直す場所は上の `responses`。`never` が「この route が宣言していない失敗」を意味することは、文言から読めない。エージェントは周りのコードから推測して直した
- **検査済みの印の型エラーは、意図を言わない（#8）**。`Property '[$brand]' is missing` は、「`.parse()` を通した値でないと渡せない」とは言わない。エージェントは `service.typetest.ts` を読んで意図に気づいた
- **typecheck が落ちると lint まで進まない**。lint の指摘は 2 回目まで見えず、一度に直せる量が分からなかった。5 回のうち 2 回は、これで増えた

## 割り引いて読む所

- 1 回だけ。Sonnet だけ。コードを自由に読めた（`service.typetest.ts` などが手がかりになった）
- **仕込んだ違反のうち、#6、#7、#11、#12 は使われていないコードだった**。消すだけで直るので、「メッセージが本当の直し方を教えたか」は測れていない。使われている違反（実際に呼ばれている所）で試す必要がある
- #10、#11 の lint は、1 回で正しく直せた。ただし、使われていない `export` や、1 行の `await` で、直すのが易しい例だった。この結果だけでは、2 本を削るか残すかは決まらない

## 直す候補（まだ直していない）

1. `no-id-cast` の文言に、「service からは作る関数が使えない。他の module の ID は素の string で渡し、`deps.ts` で印を付ける」を足す
2. `pnpm check` を、typecheck が落ちても lint まで回して、失敗を一度に出す形にする
3. `reply.failure` の `never` と、`authViewer` の `never` を、読める文言の型に差し替えられないか試す
4. 検査済みの印の型エラーに、`.parse()` を案内する手段があるか調べる（TS の型エラー文言なので、できる範囲は小さい）
5. 使われているコードに違反を仕込んだ、2 回目の実験
