# AI に新しい module を書かせた実験（comments）

作成日: 2026-10-10

「invoices と同じ形で」と頼んだだけで、規約が漏れなく伝わるかを見た実験。漏れた所を、ルールの穴として拾う。

## 条件

- 書かせた相手: Sonnet のエージェント 1 回（worktree で隔離、約 3 分、約 10 万トークン）
- 渡したもの: 依頼文だけ。仕様は「請求書へのコメント」（本文 1〜1000 文字、請求書を見られる人が読み書き、消せるのは本人か組織の admin、請求書が消えたら一緒に消える、他の組織のものは見えない、一覧は古い順、HTTP は 3 本）
- 守らせたこと: `packages/hnk/` と `.oxlintrc.json` は変えない。通らなければ緩めずに報告する。commit しない
- 注意: README を読むなとは言わなかったので、エージェントは自分で読んでいた。「文書あり」と「なし」の比較はまだ。1 回だけなので傾向とは言えない
- 結果の作業ツリーは、ブランチ `worktree-agent-acde47be32b8cea75`（worktree `.claude/worktrees/agent-acde47be32b8cea75`）に残してある。main には取り込んでいない

## 結果

typecheck・lint・テスト 49 本が通った（こちらで再実行して確認）。変えた既存ファイルは `deps.ts`・`index.ts`・`deps.test.ts`・migration だけ。

揃っていた所:

- `domain / service / routes / repo.d1` の 4 ファイル、brand 付きの入力、`Comment` への詰め替え
- 他 module（invoices）を使うとき、comments が必要な形（`CommentableInvoices`）を宣言し、deps.ts で invoices の service とつなぐ。invoices を import しない
- 外部キーでだけ他 module の表を使う（`references()`）。`no-foreign-table-reads` に合う
- 失敗は NOT_FOUND / FORBIDDEN の Result、route は `reply`、200 と `{ ok: true }` は invoices に揃えた

## 規約の漏れの候補

| 候補                                     | 何が起きたか                                                                                                                                                          | 重さ |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| 一覧に上限が無い                         | invoices はカーソル式のページング。comments は件数無制限（仕様に書かなかったが、AI は忘れうる）。共通部品（ページング）の置き場が無いことと同じ根                     | 高   |
| HTTP の正常系を試せない                  | `withViewer` が常に null なので、route 層は 401 と OpenAPI の確認だけ。未決の「テストからログイン状態を作れない」                                                     | 高   |
| ID が string 同士                        | `find(invoiceId, id)` などは、引数の順を間違えても型で止まらない。未決の ID ブランド型の裏付け                                                                        | 中   |
| 子が親の見え方を引き継ぐ流儀が割れている | payments は join、`invoice_shares` は列なし、comments は親に問い合わせ。comments の選び方だと、他の module が comments を範囲付きで読むとき、組織の線を引く場所が無い | 中   |
| domain の暗黙の前提                      | `canDelete` は `role === "admin"` だけを見る。「同じ組織」は `invoices.get` が見えるかどうかに暗黙で頼っている                                                        | 中   |
| 文字列の trim の方針                     | invoices の title は trim、comments の body は trim しない（空白だけが通る）                                                                                          | 低   |
| 子 module の route の置き方              | `/invoices` に 2 つの router を mount した。動くが、親の下に置く決まりが無い                                                                                          | 低   |

迷わず揃えられた所（規約が効いた例）: 依存の向き、他 module との繋ぎ方、200 か 201 か（invoices に揃える）。

- **文書なしでも、割れていた点（trim、システムの権限、一覧の上限）は揃った**。揃えた根拠は、コードの前例だった。報告に「payments と同じ形にした」「invoices に合わせた」が繰り返し出る
- ID の印の使い方は、`payments` の前例（素の string で持ち、`deps.ts` で印を付ける）をそのまま真似た。`deps.ts` の「ID の印はここで付ける」というコメントが効いた可能性が高い

- **結論**: この依頼では、README の有無で出来上がりの形はほぼ変わらなかった。効いているのは、README より、コードの前例（invoices と payments）と lint と型。README の「新しい module を足すとき」の表は、前例が無い判断（trim、システムの権限）の揺れを抑える保険にはなるが、前例があれば必要とは限らない
- 限界: 1 回だけ。仕様が 1 つ（comments）。コード内のコメントが説明になっている。エージェントが作業ディレクトリの外を読んでいないことは、こちらでは確かめていない（指示はした）。前例が無い種類の module（外部サービスとの連携を含まないものなど）では結果が違うかもしれない

## 5 回目（土台を替えた後。README・docs 等を取り除いた、文書なし）

土台を zod-openapi から素の Hono + Standard Schema に替え、書き方も変えた後（`.endpoint(config, fn)`、`request: { param, json }`、応答はスキーマ直書き、path は `/:id`）。同じ依頼文・同じ仕様で、README・REVIEW・docs・conventions・memo を消したコピー（ブランチ `exp/no-docs-5`、worktree `go-vs-hnk-exp8`）に頼んだ。約 2 分、約 9 万トークン。こちらで再実行して、typecheck・lint・テスト 50 本が通った。

- **新しい書き方は、前例のコードだけから、そのとおりに書けた**: `.endpoint({...}, fn)` の 2 引数、`request: { param, json }`、応答はスキーマ直書き（`200: listCommentsResponseSchema`）、`:invoiceId` の path、`errorResponses(NotFound, Forbidden)`。`json()` の説明付きや `jsonBody` を探した形跡は無い（もう無い）
- 4 回目までと共通: 4 ファイル（domain / service / repo.d1 / routes）、ID の印（`CommentId`）、trim、作成は 200、`ON DELETE CASCADE`、`invoices` の前例を真似る
- **変わった所**:
  - 請求書が見えるかの判定は、使う側の port を宣言して deps で繋ぐ形ではなく、`invoicesWithin(db, actor)`（PR #1 で入れた読みの窓口）を repo が読む形になった。reports の前例を見つけて真似た。`layer-imports` の許可（〜Within）に合っている
  - 削除の URL は `/invoices/:invoiceId/comments/:id`。コメントが指定の請求書のものかを確かめるため
  - システムも削除できる（invoices のシステムが manage 扱いなのに合わせた）
- **一覧に上限が無い**（`{ items }` だけで、`pageQuery` / `pageResponse` を使っていない）。1 回目と同じ。2〜4 回目は部品を使っていた。今回のエージェントの報告は「仕様に無いので付けていない」。lint が無いので、部品の存在は見つけやすさでしか効かず、揺れる
- 作業ディレクトリの外にある `~/.claude/skills/hono-backend`（汎用のルール）を読んだと報告している。「外のファイルは読まない」と指示したが、リポジトリの外のスキルを読んでいる。ただし「迷ったときは、汎用ルールより、このリポジトリの既存コードを優先した」とも書いている。結果への影響は、見える範囲では小さい
- 迷った点の主なもの: 見えない請求書は 404 にするか、閲覧だけの共有でも書けるか、システムの削除権限、削除の URL、並びの安定化（同じ時刻なら rowid）。前例のある判断が多い

結論: 土台を替えても、新しい書き方は、前例のコードだけで揺れずに伝わった。残る穴は、これまでと同じ「一覧に上限が無い」（部品があるのに使われない回がある）。このあと、一覧の route が `pageQuery` を使っているかを見る lint `route-lists-are-paged` を足した。**順番を逆にして、先に強く付け、例外で困るようなら外す**（あさひの案）。例外の逃げ道は `// oxlint-disable-next-line hnk/route-lists-are-paged -- 理由`。既存で外したのは `reports` の月ごとの集計 1 本（件数は `MAX_MONTHS` で検査している）。1 回だけなので、傾向とは言い切れない。
