# 実例: 月間 100 万人のサービスを Hono で作り直した話（IRBANK）と、hnk との照らし合わせ（2026-10-12）

Hono Conference 2026（10/11）の bara さんの発表「月間100万人のサービス刷新で、技術選定をHonoに振り切った話」を読み、hnk と照らし合わせた記録。この資料だけで読めるように書く。

- スライド: https://speakerdeck.com/yutobara/gekkan-100-mannin-no-sabisu-sasshin-de-gijutsu-sentei-o-hono-ni-furikita-hanashi-e49c651f-8130-48bb-b6ef-eac3cc9f358a
- 数字と事実はスライドからの引用。hnk 側の確認は main（8639a97）で行った
- 同じ日に、パッケージは [hono-kit](https://github.com/ashunar0/hono-kit) として公開した（`hnk` → `hono-kit`）。下のコード例は改名前の書き方のまま残す。4・6 で挙げたことは、7 の「やること」として hono-kit のリポジトリで入れる。4.1 と 4.2 の穴は、公開した hono-kit 0.1.1 でも実行して確かめた

---

## 1. 結論

hnk と同じ問いから始まり、同じ答えにたどり着いた、本番の規模の実例だった。問いは「人が書きやすいか」ではなく「**AI が正確かつ速く書けるか**」。答えは「選択肢を減らして迷わせない」「規約はプロンプトではなく lint に書く」。

hnk の一番の弱点は「実プロダクトで使っていない」こと。それに対して、同じ考え方で 237 万行まで回った例があると言えるようになった。

一方で、hnk に同じ系統の穴が 2 つ見つかった。認証の宣言を通らずに route を足せる（4.1）。Content-Type の無いリクエストでは、本文が黙って捨てられる（4.2）。

## 2. 発表の中身

### サービスと体制

- IRBANK。上場企業の決算・開示・市場データを、個人投資家向けに届けるサービス。月間の利用者は約 100 万人
- 旧システムは PHP。機能を足すほど遅くなっていた
- 社員 2 人と副業 4 人。2026 年 3 月に開発を始め、6 月 24 日にβを本番公開
- マージされた PR の 9 割以上に AI が関わっている

### 規模の推移（2026 年）

| 指標                  | 4/1 | 5/1 | 6/1  | 7/1   | 10/6  |
| --------------------- | --- | --- | ---- | ----- | ----- |
| TypeScript の行数     | 2万 | 9万 | 76万 | 122万 | 237万 |
| Hono の HTTP サーバー | 3   | 6   | 13   | 16    | 21    |
| `createRoute` の数    | 2   | 15  | 177  | 257   | 407   |
| 自作 lint ルール      | 0   | 0   | 17   | 21    | 34    |

### 構成と道具

- モノレポ。`apps/`（34）、`packages/`（共有 17）、`eslint-rules/`（自作 lint 34 本）、`infra/`、`.claude/`（skill）、`AGENTS.md`
- 各アプリは機能ごとに `interface / application / domain / infrastructure` の 4 層。`interface` は HTTP・外部公開 API・MCP の 3 種類
- 依存の向きは lint で強制する。**既定は全部禁止**で、許す向きだけを書く
- `@hono/zod-openapi` + Zod 4。`createRoute` が型・検査・OpenAPI を兼ねる。OpenAPI から Orval でフロントの型と hook を作り、再生成漏れは CI で落とす
- **Hono の RPC は使わない**。外部公開に OpenAPI が要るので、画面だけ RPC にすると正本が 2 つになる。407 ルート分の型推論でビルドが重くなる
- 例外クラスと番号とコードの対応を 1 か所に置き、共有の `errorHandler` を `app.onError` に渡す
- ログ: 4xx は警告として残すだけ。5xx はエラー監視に送り、利用者に返すメッセージは伏せる
- 認証: サブアプリを専用の関数で作り、「認証 → 権限 → 主体の付与」の順を固定する。**認証を通らない経路を作ってしまった事故の後、`new Hono()` で直接組み立てるのを lint で禁止した**
- テスト: `app.request()` でサーバーを立てずに結合テストを書く。新しい route には必ず 1 本付ける
- 実行環境は Node 24（ビルドは Bun）

### Hono でぶつかったこと

1. body の検査が飛ばされる。`required: true` を付けないと、Content-Type の無いリクエストは空の object として handler に届く。→ lint で止めた
2. リクエスト ID が応答から消える。`c.header()` の値は、handler が新しい `Response` を返すと載らない。→ 応答を組み立てる側で明示的に付け、テストで固定した
3. Hono のバージョンのずれで型エラー。→ 全アプリを同じバージョンに固定し、更新はまとめて行う
4. 配列の `.length()` が OpenAPI の `minItems` / `maxItems` に出ない。→ `.min().max()` に置き換えた

### やめたこと

1. 定型の仕様書を量産する（1 か月で約 300 ファイルになり、コードとずれた）。→ 難しい機能だけ人が設計し、コードと生成物（OpenAPI など）を正にする
2. skill を増やし続ける（説明文が毎回コンテキストに入る）。→ 使っていないものを消し、必要な所にだけ置く
3. 規約をプロンプトに書く（作業が長引くと抜け落ちる）。→ lint に書く
4. lint の無効化を許す（行き詰まった AI が無効化して進もうとする）。→ 無効化を禁止し、例外は理由付きのマーカーで明示する
5. PR ごとに重い検査を全部回す。→ 重いものは main へのマージ時だけ

### 持ち帰りの 3 点（発表の結び）

1. コードベースに一貫性を持たせ、AI を迷わせない
2. 意思決定は人、実装は AI
3. 振り返りから学び、見落としを lint や skill にする。lint のルールは「実装・テスト・説明文書（なぜ・違反例・直し方）」の 3 点で作る

## 4. hnk に足すもの（優先順）

### 4.1 route を足せるのは `.endpoint` だけにする（穴が実際にある）

発表の「認証を通らない経路を作ってしまった」と同じ穴が hnk にもある。`route-declares-auth` が見るのは `.endpoint(...)` の呼び出しだけで、`Router` は `Hono` を継いでいるので、`.get` などでも route を足せる。

次のファイルを lint の fixture に置いて確かめた。8 本のルールのどれも指摘しなかった（指摘 0 件）。

```ts
import { createRouter } from "hnk";

export const tmpxRouter = createRouter().get(
  "/secret",
  () => new Response("no auth, no responses"),
);
```

認証の宣言も、`responses` の約束も、`reply` も通らない。`c.json` は `route-replies-through-reply` が止めるが、`new Response()` を返せばすり抜ける。

hono-kit 0.1.1 で、この route にリクエストを送ると 200 が返る（認証も検査も通らない）。

→ HTTP の入口（routes・webhook）では、`.get` / `.post` / `.put` / `.patch` / `.delete` / `.all` / `.on` と `new Hono()` を止める lint を足す。

### 4.2 Content-Type の無い本文を 400 にする（穴が実際にある）

発表の「body の検査が飛ばされる」と同じ系統。zod-openapi の頃は `jsonBody` で `required: true` を必ず付けていたが、今の検査（`router.ts` の `check("json", …)`）は Hono の `validator("json")` に任せている。Hono は Content-Type が JSON でないとき、本文を読まずに `{}` を検査に渡す。

hono-kit 0.1.1 で確かめた結果:

| 宣言した本文                            | 送ったもの                         | 結果                              |
| --------------------------------------- | ---------------------------------- | --------------------------------- |
| `{ title: string }`（必須の項目がある） | `{"title":1}`、Content-Type 無し   | 400（`{}` が検査で落ちる）        |
| `{ note?: string }`（全部省略できる）   | `{"note":123}`、Content-Type 無し  | **200、handler には `{}` が届く** |
| `{ note?: string }`                     | `{"note":123}`、Content-Type: JSON | 400                               |

必須の項目が 1 つでもあれば落ちるので事故にはならない。全部省略できる本文（部分更新など）では、間違った本文が「何も変えない成功」として通る。

→ `json` を宣言した route では、Content-Type が JSON でなければ 400（ValidationError）にする。`check("json", …)` の前に 1 つ足す。

### 4.3 lint の無効化には理由を必須にする

`route-lists-are-paged` の例外は `// oxlint-disable-next-line hnk/route-lists-are-paged -- 理由` で書く運用にしている。ただ、理由の無い無効化や、ファイルごとの無効化を止める仕組みは無い。

→ `-- 理由` の無い `oxlint-disable` を止める。ファイル全体の無効化（`oxlint-disable` を先頭に置く形）は認めない。

要確認: oxlint 自体に「理由を必須にする」設定があるかは確かめていない。無ければ、コメントを見るルールを hono-kit の lint に 1 本書く。

### 4.4 ログを設計する

hnk のログは今 3 か所だけ（`onError` と `createWorker` の想定外の throw、reminders の cron）。リクエストのログ、失敗のコード、誰の操作か、かかった時間は残っていない。次の形で入れる。

- **書くのは入口と hnk だけ**。core と outbound は書かない（`no-clock-outside-inbound` と同じ考え方で lint にできる）
- **1 リクエスト 1 行の構造化ログを hnk が出す**。`reply.failure` は hnk を通るので、宣言した失敗のコードをアプリが何も書かずに残せる。項目は route のパターン、番号、失敗のコード、actor の ID、組織、かかった時間、リクエスト ID
- **4xx と 5xx を分ける**（発表から）。`Failure` の種類で振り分けを hnk が決める。5xx は利用者に返す文言を伏せる
- **リクエスト ID は応答を組み立てる側で付ける**（発表から）。`c.header()` は新しい `Response` を返すと消えるので、`reply` で付ける
- cron とキューも `createWorker` が同じ形で 1 行出す
- ライブラリは足さない。Workers では `console.log` に object を渡せば構造化して扱われる。「依存は hono だけ」を崩さない

### 4.5 lint のルールに説明文書を付ける

hnk のルールは実装とテスト（文言まで固定）があるが、説明文書が無い。ルールごとに「なぜ・違反例・直し方」を書く。ルールが増えたときに効く。

### 4.6 route を足したらテストも足す

`g module` は `routes.test.ts` を出すが、後から route を足したときの決まりは無い。README の未決（失敗のコードごとにテストがあるか）と一緒に決める。

## 5. 判断が分かれていて、見直す材料にするもの

- **RPC の型の重さ**: hnk は `hc` の型が通ることを利点にしている。発表では 407 ルートで型推論が重くなり、RPC を外した。「でかいプロダクトにも」を言うなら、ルートを数百本に増やした状態の `tsc` の時間を測る。重ければ「OpenAPI を正にして、RPC は任意」の道を用意する
- **OpenAPI からフロントの型を作る道**: hnk は `hnk/openapi` で文書を作れる。Orval などでフロントの型を作り、再生成漏れを CI で落とす流れを、雛形かスキルで示すか
- **入口としての MCP**: 発表では interface の 1 つに MCP がある。hnk の inbound（routes・webhook・cron・queue）に `mcp.ts` が加わる日は近い。来たら「2 つ目の入口」として足す
- **Workers 以外の実行環境**: 発表は Node。hnk の雛形は Workers + D1 前提。仕組み（`router.ts` など）は素の Hono なので動くはずだが、`createWorker` や雛形は Workers 専用。どこまでを hnk の範囲にするかを決める
- **Hono のバージョンの固定**: hnk は Hono の `Handler` / `ToSchema` の型に追従する責任を持っている（docs/16）。アプリと hnk で Hono のバージョンがずれたときの型エラーを、どう防ぐか（peerDependencies の範囲、雛形での固定）

## 6. スライドを読み直して足したもの

最初のまとめで拾えていなかったもの。どれも hono-kit の今と照らして確かめた。

### 6.1 AI の入口の文書が、配布物に入っていなかった

発表では `AGENTS.md` を 200 行以内に保ち、コマンド・構成・規約へのリンクだけを書く。細かい規約は lint と、必要なときだけ読まれるルール文書に振り分ける（p.44、p.60）。

hono-kit の AI 向けの手順は、作者の手元のスキル（`~/.claude/skills/hnk`）にしか無かった。`pnpm create hnk` で作ったアプリには入っていないので、ほかの人の AI には届かない。

→ 雛形に `AGENTS.md`（と、それを読み込むだけの `CLAUDE.md`）を入れる。必要なときだけ読む手順（module をまたぐとき、cron やメールを足すとき）はパッケージの `docs/` に置き、`node_modules/hono-kit/docs/…` でリンクする。版を上げれば一緒に新しくなる。

### 6.2 雛形の lint で any と vi.mock を止めていなかった

発表の「始める順番」の最初は「tsconfig の 3 設定と、any を禁止する lint」（p.59）。テストでは「モジュール丸ごとの差し替えの禁止」を lint にしている（p.36）。hono-kit の雛形の lint は、hnk のルール 8 本と `import/no-cycle` だけだった。

→ `typescript/no-explicit-any` と `vitest/no-restricted-vi-methods`（`vi.mock` / `vi.doMock`）を雛形に足す。依存は deps で渡す、repo は本物の D1 で試す、という hono-kit の方針とも合う。

### 6.3 業務の値にも印を付ける（きっかけ待ち）

自作 lint の 3 本は「証券コードや決済情報を生のまま扱わせない」もの（p.36）。hono-kit の印と `no-id-cast` は ID だけが対象。金額やコードのような業務の値にも同じ印を付けて `as` を止める形に広げられる。実プロダクトで要る値が出てから。

### 6.4 OpenAPI をファイルに出し、operationId を書けるようにする（きっかけ待ち）

発表では、route を変えたのに OpenAPI の JSON を作り直していない PR を CI で落とす（p.27）。`operationId` がそのまま生成されるフロントの hook の名前になる（p.26）。hono-kit の OpenAPI はリクエストのたびに `/openapi.json` で作るだけで、設定に `operationId`・`tags`・`summary` の欄が無い。5 の「OpenAPI からフロントの型を作る道」を取るときに一緒に入れる。

### 6.5 429 の種類が無い（記録だけ）

発表のエラーの表には `TooManyRequestsError` → 429 `RATE_LIMITED` がある（p.29）。hono-kit の種類は 5 つ（unauthenticated / forbidden / notFound / conflict / upstream）。「既存のどれでも言い表せない失敗が現れたら足す」の決まりどおり、要る場面が来たら足す。
