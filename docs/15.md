## 2. 何が変わったか(確認済み)

### 非推奨

`src/helper/factory/index.ts` の `@deprecated`:

| 旧 | 新 | 備考 |
| --- | --- | --- |
| `createHandlers` | `defineHandler()` | 「次のメジャーで削除」。ミドルウェアはハンドラーの前に並べて渡す |
| `createMiddleware` | `defineMiddleware()` | 同上。`Factory` のメソッド版と単体関数版の両方 |

- `src/` 配下(テスト除く)で `@deprecated` が付いているのは上記の factory 関連だけだった
- `createFactory` / `createApp` / `initApp` は非推奨になっていない
- ただしこれは JSDoc タグを検索しただけ。タグのない破壊的変更や、すでに削除済みのものは拾えていない

### `defineHandler` の2つの形(`src/helper/factory/define-handler.ts`)

```ts
import { defineHandler } from 'hono/factory'

// 1. オプションなし: ミドルウェア... + ハンドラー
app.get('/ping', defineHandler(() => ({ pong: true })))
app.get('/me', defineHandler(auth, (c) => c.get('user')))

// 2. オプションあり(カリー化): 検証済みの値は第2引数で受け取る
app.post(
  '/users/:id',
  defineHandler({
    param: ParamSchema,
    json: BodySchema,
    response: UserSchema,
  })(async (c, { param, json }) => {
    c.status(201)
    return { id: param.id, ...json }
  })
)
```

- 戻り値の変換(`toResponse`): オブジェクト→JSON、文字列と `HtmlEscaped`(JSX)→`c.html()`、`null`/`undefined`→204、`Response`→そのまま
- 検証対象: `param` / `query` / `header` / `cookie` / `form` / `json`、加えて `response`
- 各検証は Standard Schema か関数。検証済みの値は第2引数と `c.req.valid()` の両方で取れる
- 失敗時は `HTTPException`(リクエスト側400、レスポンス側500)。`res` は `{ error, issues }` のJSON、`cause` に生のissues
- ミドルウェアは検証より先に走る(ファイル内の独自 `compose` で実行)
- `handler.validations` にオプションが載るので、OpenAPI生成などから読める
- ステータスは `c.status()` で設定し、型には載らない(`c.json()` を返すと型に載る)
- `response` を指定すると、ハンドラーが返す JSON の `Response` は型で弾かれる
- `@experimental`
- `Factory` クラスにも `defineHandler` / `defineMiddleware` が生えている

## 3. `defineHandler` の価値(意見)

一言で言うと、**ハンドラーの入口(入力)と出口(出力)の約束を1か所に宣言して、型と実行時チェックを同時に得られる**こと。

- 検証の書き忘れが起きにくい(オブジェクトで宣言するので、無いことが目立つ)。PR #5531 の説明にも、AIエージェントも同様という趣旨の記述があった
- ミドルウェアのEnvや検証済み入力が型付きで繋がる。`createHandlers` の10個のオーバーロードが消えた
- `return` した値がそのままレスポンスになり、書く量が減る
- 出口(`response`)も契約になる
- `handler.validations` からツールがスキーマを読める
- コアの実装は変えない、ただのヘルパー

## 4. 設計への感想(意見)

良い点
- 型の見通しが良くなった(オーバーロード→可変長タプル)
- 認証ミドルウェア → 検証の順で走る
- 検証結果を第2引数で受け取れる
- Standard Schema で依存が増えない

気になる点
- ステータスが型に乗らない(`hc` で `201` / `404` を型で分岐できない)
- 文字列が `text/html` になる
- 1つの関数が「即ハンドラー」と「カリー化」の2つの顔を持つ
- ミドルウェア合成を独自実装していて、`app.use` と細かい挙動がずれないか

## 5. issue候補(要再現確認)

ユーザーは `defineHandler` のレビューに関わった立場。以下は、設計の意図を聞くべき点でもある。

### 5-1. 素の文字列が `text/html` で返る(最優先で確認)

`toResponse` が文字列を `c.html()` に渡している。`c.html()` は文字列をエスケープしないので、ユーザー入力をそのまま返すと反射型XSSになりうる、という仮説。

提案: 素の文字列は `text/plain`、`HtmlEscaped`(JSX / `html` タグ)だけHTMLにする。

再現(リポジトリ内に置いて、相対importで実行):

```ts
// scratch/repro-string-html.ts
import { Hono } from '../src/hono'
import { defineHandler } from '../src/helper/factory'

const app = new Hono()
app.get('/', defineHandler((c) => c.req.query('name') ?? ''))

const res = await app.request('/?name=<script>alert(1)</script>')
console.log(res.headers.get('content-type')) // text/html になっていないか
console.log(await res.text())                 // エスケープされていないか
```

- [ ] Content-Type が `text/html` か
- [ ] 本文が生の `<script>` のままか
- [ ] 意図された仕様か(PR上の議論、ドキュメントの記述)

### 5-2. ステータスごとのレスポンス定義

案: `response: { 200: UserSchema, 404: ErrorSchema }` のようなマップ形式。`hc` の型とOpenAPIの両方に効く。#2439(レスポンス検証の要望)の議論を先に確認する。

- [ ] `hc` から見た型で、ステータスが落ちることの確認
- [ ] #2439 での議論との重複確認

### 5-3. パスとスキーマの不整合が型で検出できない

```ts
const h = defineHandler({ param: v.object({ id: v.string() }) })(
  (c, { param }) => param.id
)
app.get('/users/:userId', h) // 型エラーになるか、実行時に常に400か
```

- [ ] 型エラーにならないことの確認
- [ ] 実行時に常に400になることの確認

### 5-4. 細かい点

- issues の `path` が `.` 結合の文字列で、キー名に `.` を含むと曖昧になる(`toValidationIssues`)
- `response` 指定時にハンドラーが `Response` を返すと、実行時は検証をすり抜ける

```ts
defineHandler({ response: v.object({ ok: v.boolean() }) })(
  (c) => c.json({ ok: 'not a boolean' }) as any
)
// 500にならず、そのまま返るか
```

## 6. OpenAPI系との比較(記憶ベース、最新は未確認)

`@hono/zod-openapi` の `createRoute` + `app.openapi()` との違い。

| | zod-openapi | defineHandler |
| --- | --- | --- |
| 単位 | ルート全体(メソッド・パス・入力・ステータス別出力・説明) | ハンドラー単体 |
| アプリ | `OpenAPIHono`(別クラス) | 普通の `Hono` |
| スキーマ | Zod前提 | Standard Schema(非依存) |
| OpenAPI生成 | する | しない(`validations` を公開するだけ) |
| ステータス別レスポンス | 型に乗る(`hc` でも効く) | 乗らない(現状) |

- 5-2 は zod-openapi がやっていることの取り込み、5-3 は zod-openapi ならパスをルート定義に持つので起きにくい
- Standard Schema 系のサードパーティ(`hono-openapi` など)もあった気がするが、自信がない。要調査

## 7. 「OpenAPI前提」vs「ヘルパー+生成」(意見)

- 前者(`app.openapi`): 仕様が主役で、1か所にまとまる。成熟していて確実。代わりにZodと専用クラスに縛られ、OpenAPIの語彙に合わせる必要がある
- 後者(ヘルパー+docs生成): 契約が先でdocsは派生物。依存の向きがきれいで、スキーマ非依存。代わりにOpenAPIに必要な情報(summary / tags / ステータス別レスポンス / example)が足りず、足すと前者に近づく
- 使い分け: OpenAPIが成果物(外部公開、クライアント自動生成)なら今は前者。型と検証が主目的でdocsはおまけなら後者

## 8. AIエージェント駆動開発の観点(意見)

人間がコードをほぼ読まない前提だと、基準は「機械で強制・検証できるか」と「人間がレビューする面がどこか」。

- 前者の強み: レビューする面が仕様1か所に集まる。AIの学習データが多い
- 後者の強み: 書き方が1つに絞れ、lintで縛りやすい。依存が軽い
- 運用案: 実装は後者の形で書かせ、生成したOpenAPIをCIでdiff出力し、人間はそのdiffだけレビューする

### 成熟度を抜きにして、自由に作れるなら後者が強い(意見)

- 契約とロジックが同じ場所にあり、変更が1つのdiffに出る
- 覚えることが1つで、規約をlintで機械的に守らせやすい
- 契約から、OpenAPI以外(SDK、テスト雛形、MCPツール定義)も派生できる
- OpenAPIの語彙に縛られない

勝つための条件:
1. ステータス別レスポンス(エラー含む)を宣言に入れる
2. summary / tags / security / example などのメタ情報を宣言に入れる(必須にもできる)
3. 宣言にない返し方を塞ぐ(`c.status()` や素の `c.json()` の直書きを型と実行時の両方で禁止)
4. ルート登録時に、パスのパラメータとスキーマのキーを突き合わせる
5. 契約をシリアライズできる中間表現として取り出せる
6. エラーの形を標準化する

注意: 全部入れると情報量は `createRoute` とほぼ同じになる。勝ち筋は情報量ではなく、**コロケーション・依存の向き・拡張のしやすさ**。中間表現を独自に作るとツールが育たないので、「OpenAPIを中間表現にする」手もある。

## 9. 自作する場合の方針(意見)

### 「全部自作」より「薄い自分の層」

- 自分で持つ価値が高い: 契約の中間表現(ステータス別レスポンス、メタ情報、エラーの形)、規約(lintルール、必須項目)、生成器
- 上流を使う: ハンドラーの配管(特に型)。`defineHandler` はEnv合成や検証済み入力の型付けで型パラメータが8個ほどあり、自前保守は重い
- 足りない部分は、自作するだけでなく上流にissueとして出す(通れば自作が減るし、通らなくても設計の材料になる)

### v4までの資産+自作(`defineHandler` に縛られない場合)

- きつくないと思う。むしろ現実的
- 公開APIで組める: `validator()` を対象ごとに挟み、`c.req.valid()` で取り出し、自分のレスポンス変換を足す。内部API(`define-handler.ts` が使っている `getValidationTarget` など)に触らずに済む
- 実行時の処理は軽い(`defineHandler` 本体も150行ほど)
- 難所は型。`Handler<E, P, I, R>` の `I`(入力)と `R`(レスポンス)を正しく載せないと、`hc` の型や `c.req.valid()` が壊れる。ただし自分のプロジェクト専用に絞る(スキーマライブラリを1つに固定、Env合成は最小限)と簡単になる
- Honoのライセンスは確かMITで、型の作りは参考にしやすいはず(要確認)
- リスク: Honoの `Handler` / `Input` まわりの型変更への追従。v5の破壊的変更の全貌は未把握
- `defineHandler` に縛られない利点: experimentalの変更に巻き込まれない。上流が育ったら自作の層を薄くして乗り換えられる設計にしておく

### 最初の一歩(提案)

1. `validator()` を束ねて、戻り値を変換するだけの最小版を作る
2. **最初に `hc` の型が通るか確認する**(ここが一番の難所)
3. 条件2(メタ情報)と条件3(抜け道を塞ぐ)だけ満たす小さなラッパーで、エージェントがどう使うか観察する
4. 生成物(OpenAPI)をCIでdiff出力する運用を試す
