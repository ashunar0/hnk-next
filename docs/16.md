# 土台を zod-openapi から、素の Hono + Standard Schema に替えた（2026-10-09）

`exp/own-endpoint` の記録。main に取り込み済み（56d9c09）。

## きっかけ

`createEndpoint` は `@hono/zod-openapi` の `createRoute` の形に乗っていた。あさひから「依存を前提にするのがどうか」「ヘルパーを自分で持って、その上から OpenAPI や zod、valibot と連携する方が、長期で見て色々やりやすいのでは」という指摘があった。

ぼくは最初、これを「今は作らない（YAGNI）」と退けた。あさひの引き算は後回しではなく、**そもそも要らないものは使わない**という意味で、Hono が好きな理由（コアが小さい、依存ゼロ、Web 標準、要るものを選んで足す）と同じだった。zod-openapi は別クラス（`OpenAPIHono`）と Zod と OpenAPI の語彙を、まとめて持ち込む。それは引き算の向きと逆だった。

## 決めたこと

| 点       | 決めた形                                                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 土台     | 素の Hono。`Router`（`Hono` を継いだクラス）が `.endpoint(config, fn)` で登録する                                                                                        |
| スキーマ | Standard Schema を満たすものなら何でも。zod と valibot で確かめた                                                                                                        |
| OpenAPI  | 別の部品 `hnk/openapi`。登録された宣言（handler に貼ったシンボル）を `app.routes` から読んで作る。JSON Schema への変換はスキーマのライブラリ自身（Standard JSON Schema） |
| method   | 小文字（`app.get` と同じ）                                                                                                                                               |
| path     | Hono の `/:id`。OpenAPI の文書には `{id}` に変換して出す                                                                                                                 |
| 登録     | スプレッド（`...createEndpoint`）をやめて、config と handler の引数 2 つ                                                                                                 |
| 入力     | `request: { param, query, header, cookie, json }`。キーは `c.req.valid("…")` の名前と同じ                                                                                |
| 出力     | スキーマをそのまま書く。説明を OpenAPI に出したいときだけ `json(schema, "説明")`                                                                                         |

## 作ったもの（`packages/hnk/src/`、約 400 行）

- `standard-schema.ts`: Standard Schema の型（型だけ。依存は増えない）
- `route-types.ts`: config から、`c.req.valid()`、`reply`、`hc` の応答の型を決める型
- `router.ts`: `Router` と `createRouter`。検査は Hono の `validator()` の上で Standard Schema の `validate()` を呼ぶ
- `openapi.ts`: 文書の生成。表せない型は「何でも」にして止めず、`libraryOptions` で出し方を渡せる（アプリ側で zod の日付を日時の文字列にしている）

## 確かめたこと

- `pnpm check` が全部通る（型、lint、テスト 46 件）。`hc` の型テスト（`rpc.typetest.ts`）と `reply` の型テストも、route の書き換え以外はそのまま通った。一番の難所だった「`hc` の型が成り立つか」は、zod-openapi の型を参考に Hono の `ToSchema` で組んで通った
- valibot で書いた route が動く（`test/valibot.test.ts`）。入力の検査、`transform` の後の型、`reply.failure`、OpenAPI の文書まで。valibot は単体では JSON Schema を出せないので、文書に出したいものだけ `toStandardJsonSchema` で包む
- `@hono/zod-openapi` は package.json からもロックファイルからも消えた
- 新しく効くもの: path の `:name` と `request.param` のキーの食い違いが、型エラーになる（`endpoint.typetest.ts`）。宣言していない入力は `valid()` で読めない

## 依存の足し方

OpenAPI が要らなければ `hnk/openapi` を import しないだけでよい（バンドルに入らない）。要る場合、zod 4 なら依存は増えない（zod 自身が JSON Schema を出す）。valibot なら、アプリに `@valibot/to-json-schema` を足す。足す場所は hnk ではなくアプリの package.json。文書を見るための画面（Swagger UI など）は hnk は持たない。

## 残っていること

- `page-schema.ts`（`cursorSchema`、`pageQuery`）は zod 固定。他のライブラリでは使えない
- Hono の `Handler` / `ToSchema` の型に追従する責任が、hnk に移った（今は 4.13.13 で確認）
- `reply(200, body)` を `reply.ok` / `reply.err` に揃えるかは、きっかけ待ちのまま
- 設定の形（`request` のキーの名前、応答の書き方）は、使ってみて揺れたら見直す
- 新しい土台で、AI に書かせる実験を回し直す価値がある（形が変わったので、同じ形で書けるかを測り直す）
